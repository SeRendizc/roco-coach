### 1.2 写入时机与原子性

- **服务端**：没有任何运行时落盘。全仓 `src/**` 里真正的写盘调用**只有**
  `src/coach/cloud-replay.mjs:85/123 mkdirSync(...)` + `:99/130 appendFileSync(...)` ——
  那是**离线回放/录制夹具**（把云端 LLM 往返写成 JSONL），不是产品数据。
  （其余 `truncated` 命中都是变量名/字段名，不是文件截断 —— grep 读数见 §7。）
  Python 侧 `coverage.py:831` / `regression.py:482` / `support.py:188` 的 `open(path,'w')` 都是
  **CLI 报告生成器**（argparse `--out`），运行中的 service 只写 stdout/stderr/socket（`service.py:3199/3209/3487`）。
- **原子替换 / fsync**：全仓 `src/**`、`roco/src/**` **0 处** `rename`/`fsync`/`tmp+rename`（grep 读数见 §7）。
- **浏览器**：`localStorage.setItem(key, JSON.stringify(整个对象))`；浏览器保证**单键写原子**，
  但「读→改→写」整体**不原子**（多标签/页面+面板并发会丢对方写入，见 R3）。

### 1.4 缺口（异常恢复）

- **R1** 对局状态只存内存、且 `stop()` 无条件清空：**空闲 5 分钟 = 丢局**（探针 §5 实测 404）。
- **R2** Node 重启/断电无任何恢复入口：没有对局快照文件、没有"恢复上一局"接口（`GET /api/bootstrap` 只给会话）。
- **R3** 浏览器侧对局（`battleId`/`view`/`history`）不落盘：刷新即"沉默清空"——**正是 10-PLAN 明令禁止的恢复方式**。
- **R4** 没有"明确的刷新/断线行为"定义：当前行为是"页面从零开始 + 服务端会话变孤儿"，
  玩家看不到"你刚才那局还在/已经没了"的任何提示（`b3RejectGuard` 只在出招被拒时说话）。
- **R5** 无归档/清理策略：`sessions.clear()` 直接丢、无 dump；`SKILL_SUPPORT_CACHE`/`answerCache` 同理；
  客户端记忆有**静默截断**：`memory.js:112 journal.slice(-240)`、`:185 lessons.slice(-12)`、
  `:104 events.slice(-12)`、`dialogue.slice(-8)` ⇒ 超出即丢且**不记账**。
- **R6** 无"恢复证据"：恢复矩阵要求「只恢复有证据的数据」（10.3），当前连"上一局是什么"都没留（match_id 只在内存）。
- **R7** 10.6 的资源归属没有登记面：`index.js:1127-1130` 只保证 close 时带走自己的 Python 子进程；
  没有"我起了哪些进程/端口/浏览器"的清单可供 10.6 逐条核对。

### 3.2 缺口

- **G1（fail-open 方向）** CAS **只在调用方带了 `state_version` 时才检查**（`:2451-2452` 注释逐字承认：
  「只在调用方**明确带了**版本时检查（老客户端不带 ⇒ 行为不变）」）⇒ 任何不带版本的调用方（旧页面/脚本/第三方）
  都能重复结算。10.2 的"重复请求"反例必须**同时**覆盖"带版本"与"不带版本"两条。
- **G2** `match_id` **不是每局唯一**（`:2404-2406` 注释自认：由公开开局事实派生，同规则同己方队伍两局会相同）
  ⇒ 串局守卫对"同队重开"不敏感；唯一性由 `battle_id`（`s2-xxxxxxxx`）承担。
- **G3** 没有**幂等键**（无 `Idempotency-Key`/`decision_id` 去重表）：网络重试若在服务端已结算后到达，
  带版本的会被 CAS 挡住 ✓；不带版本的会**重复结算**（同 G1）。
- **G4** `inFlight` 是**进程内**锁；Node 侧没有跨实例/跨重启的保护，也没有"请求指纹→结果"的缓存可回放。
- **G5** 刷新后**无恢复**：`battleId` 不落盘（§2.3），服务端会话仍活着却无人认领（直到 5 分钟空闲被清）——
  既丢局又留孤儿。
- **G6** 「结果已结算但响应丢失」没有对账入口：客户端只知道自己看到的 `state_version`，
  没有 `GET /battle/status`（按 battle_id 查当前版本）这类探针 ⇒ 断网重连后只能靠 409 撞墙（10.2 要实测）。

### 4.2 玩家/调用方看得到什么

- **玩家**：对局中 `roco.js:899-901` 把 `about-ruleset` 写成「`<ruleset_id>` · 本局状态版本 `<state_version>`」；

### 4.3 版本不一致时的行为（现状）

| 场景 | 行为 | 判定 |
|---|---|---|
| 请求声明了别的 `ruleset_id` | Python `version_mismatch` → **409**，不装载别的版本（`service.py:61/565-658`） | **fail closed** ✓ |
| 桥与服务 `protocol_version` 不一致 | `handshake()` 返回 `VERSION_MISMATCH`（`roco-client.js:770-789`） | **fail closed** ✓ |
| 对局 `match_id`/`rules_version` 与本地绑定不符 | 409 `match_mismatch`（探针 §3） | **fail closed** ✓ |
| 结果的 `state_version` 过期 | adapter 丢弃（`game-adapter.js:935-942`）、页面提示重看（409 `stale_state`） | **fail closed** ✓ |
| Node 的 `RULESET_ID` vs 引擎 `/health.ruleset_id` | **两者并列返回、无人比对**（`roco-service.js:2094` 与 `:2095`） | **缺口 V4** |
| 静态资源已更新但后端旧进程 | 无检测（`asset_refreshes` 只在 404 miss 时自愈，`index.js:184-198`） | **缺口 V5**（= 10-PLAN 的必做反例） |

### 4.4 缺口（版本）

- **V1** 没有 **HEAD + dirty hash**、没有构建指纹（10.5 明令要求）——`status()` 只有 `runtimeVersion` 常量。
- **V2** 三个版本字符串（`0.11` / `0.1.0` / ruleset id）**互不校验**，也没有任何判据钉住它们（grep 未见断言）。
- **V3** `package.json` 无 `version`；无法从产物判断"跑的是哪一版"。
- **V4** Node 的 `RULESET_ID` 与引擎 `health.ruleset_id` 不比对（应当 fail closed 或至少在状态面点名）。
- **V5** 「静态文件比进程新」无检测（10-PLAN 必做反例的另一半）。
- **V6** 玩家界面不显示运行版本/构建时间；`roco.html:767` 还留了一份硬编码 ruleset 默认值（第二事实源）。

## 5. 实现顺序草案（小步可冻结 · 每步判据 + 两向变异）

> 口径：每步只做一件事、能单独冻结；判据必须**双向**（正向 + 把修复撤回会红）。

| 步 | 动作（最小） | 判据（正向） | 两向变异 |
