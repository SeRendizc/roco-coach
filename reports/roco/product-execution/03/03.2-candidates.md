## 2 · 候选协议（`rc604-opponent-candidates/v1`，机器可读）

两条在线入口（都在 `ONLINE_ENTRYPOINTS` 里登记）：

```js
readOpponentView(view)            // view → publicFacts（只读 6 条白名单路径；来源写死在适配器里）
buildOpponentCandidates({catalog, publicFacts | view, skillPool, proposedLoadouts, budget})
  → {protocol, available, provenance, universe_size, budget, candidates[], contradictions[],
     rule_ledger, leaked_fields, evidence, unverified}
```

**每条候选**（`candidate_protocol.fields` 逐字列出）：

| 字段 | 内容 | 来源 / 等级 |
|---|---|---|
| `candidate_id` / `species_id` / `name` | 物种身份 | 冻结图鉴（`catalog.featureFor()`） |
| `basis` | `observed`（公开史里见过）/ `inferred`（规则推的） | 已观察与推测**分字段**，不混用 |
| `types` / `spe` / `spe_status` / `spe_source` | 物种级属性与速度 | 冻结图鉴（`species-race` / `knowledge_only`） |
| `speed_band` / `band_source` | 速度档 + 「工程三分位、不是游戏字段」的说明 | RC-303 `speedBandFor()` **现算** |
| `in_filtered_pool` / `inferred_rank` | 规则池命中 / 缩减序位 | `applyRules()` 账本 |
| `observed{slots, reveals, visible_panel}` | 位次、`revealed_via` + `revealed_turn`、场上那只的可见面板 | `view.seen_roster` / `view.opponent.field` |
| `skills{known_used, possible, pool_tier, grade, legality}` | 已出招（公开事实）与可学池（分级）分开；四技能合法性 | 见 §2.1 |
| `individual_range` | `known:false` + 观测到的**物种级**数值 + 「保留多解」声明 | 个体真值不在公开面 |
| `actions` | 只登记已打出来的技能 + 可能动作类别 | 明确写「不预测下一手」 |
| `sources` / `unknowns` / `rules_version` / `evidence` | 逐项出处、未知项、规则版本、证据行 | `evidence()` 形状（与 RC-302/303/304 同源） |

### 2.2 四技能合法性（必做反例②）

`legalSkillLoadout({pool, proposed, limit:4})` → `{ok, kept, excluded[{skill_id, why}]}`，三类不合法：
不在可学池 / 重复 / 超四技能。候选里 `skills.legality` 同时保留 `proposed`，审计用**独立复算**核对
（`ILLEGAL_LOADOUT_IN_CANDIDATES`）。

### 2.3 矛盾通道（不静默）

`contradictions[]` 现有两类：`OBSERVED_NOT_IN_FILTERED_POOL`（已亮明却被规则筛出池子）、
`USED_SKILL_NOT_LEARNABLE`（已出招却不在可学池）。**已见候选永远保留**，矛盾如实报出（以观察为准）。

### 2.4 预算（R7 的骨架；威胁保留策略留给 03.5）

`budget = {limit:24, rule, kept, observed_kept, inferred_kept, truncated, dropped_count, pool_summary}`；
缩减规则是**可解释、可复算**的一条：`observed_first（按 slot 升序）→ inferred（①有冻结学招表
②与已亮明速度档同档 ③species_id 升序）`；被裁掉的部分留下 `pool_summary.dropped_by_band` 分布。

## 4 · 必做反例

### 反例② 已知不合法的技能组合不得进入候选（**已落地并有牙**）

夹具物种 `pet_000417`（冻结学招表 45 条），三种不合法各跑一次（`raw-03.2-situations.txt` 末段）：

| 输入 | `ok` | `kept` | `excluded`（逐条理由） |
|---|---|---|---|
| `[…3 条合法, skill_999999]` | false | 3 条合法 | `skill_999999: 不在这只的可学池里（冻结学招表 / on-demand-builds）` |
| `[p0, p0, p1, p2]` | false | `p0,p1,p2` | `p0: 同一个技能出现两次：四技能不许重复` |
| `poolIds[:5]`（五技能） | false | 前 4 条 | `p4: 超过四技能上限（4）：多出来的不进候选` |

必红：把重复技能塞回 `kept` ⇒ 审计 `ILLEGAL_LOADOUT_IN_CANDIDATES`（独立复算发现不一致）；
反向控制：合法候选集合审计 `ok=true`（不许误判）。

### 反例① 同一公开伤害由两种个体配置都能解释 ⇒ 两者都留（**协议前提已钉，落点在 03.3**）

候选的 `individual_range = {known:false, individual_values_visible:false, scenarios:[观测到的**物种级**数值],
note:'个体面板 / 天赋 / 性格不在公开面：同一份可见伤害可能由多种个体配置解释 ⇒ 保留多解（03.3）'}`；
候选里**没有** `nature` / `talent` / `panel` 等个体真值字段（测试逐条断言）。
⇒ 协议不允许把「个体配置」收敛成单点；**基于可见伤害的多解枚举与收窄在 03.3 实现**。
