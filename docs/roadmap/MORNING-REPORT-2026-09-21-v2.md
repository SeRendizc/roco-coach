## 3. 这一夜修掉的真 bug（每条都能复现）

**这些不是我为了交差找的活，是测试与回归抓出来的。**

### 3.1 桥的隐藏信息边界漏了一层（真漏洞）

上一版我把 `state.seed` 的例外去掉了，但**桥自己的键名表少了 5 个键**
（`pendingenemy` / `pendingplayer` / `pendingenemyaction` / `pendingplayeraction` /
`replacequeue`）。而 `env.serialize()` 里对手待执行动作的真实键名就是 `_pending_enemy`
—— 也就是说**私有状态能从第一层（Node 桥）穿过去**，只剩 Python 兜底。

修法：三份词汇表（Python 服务 / Node 桥 / 浏览器工具层镜像）补成一一对应，
并新增一条**跨文件比对测试**直接读三个源文件比集合 —— 任何一侧改单边都会变红，不靠注释约定。

### 3.2 「真链路能出计划」以前没有任何测试证明

`bridge.test.js` 只证明了「缺 public 会被拒」；工具层测试用的是假客户端。
两边都绿而真实链路对不上完全可能（T02 阶段就是这样）。
新增 `npm run test:plan-e2e`：公开状态由 **Python 引擎现场生成**，
端到端跑通 toolbox → 桥 → HTTP → 真服务，并反证：

- 同一公开观察 + 两个不同真实内部 seed → 公开面逐字节一致、结论一致、
  **请求体里连真实 seed 的取值都不出现**；
- `state.seed` / `state.foo.seed` / `state.history[0].seed` / 对手待执行动作
  在客户端就拦下，用**记账 HTTP 端点**证明请求数为 0（并配一条「干净状态确实发得出去」的对照组）。

### 3.3 补位阶段的规划**从来没有真的算过**（F02 回归抓到）

引擎在 `phase=replace` 时会拒绝 `step_joint`（要求用 `step_replace`），
而 planner 的 rollout 一律调 `step_joint` —— 于是每个分支都被 `except` 丢弃，
表现是三个字段互相矛盾：`branches_evaluated=0`、`timed_out=False`、`coverage=1.0`，
而推荐其实来自「步骤失败后原样返回的状态」。现在补位走 `step_replace`，
并新增 `dropped_branches`（丢弃了几个分支、为什么）与 `no_counter_branches`。

### 3.4 服务能力表在说假话

`/health` 的 `capabilities` 把 `team.evaluate` / `team.compare` / `battle.plan`
报成 `false`，而这三个端点早就接上引擎了。调用方看到 `false` 会绕开它们。
现在改为 `true`，并新增测试逐条核对「声明为 true 的必须真的答得上来」。

### 3.5「还没做」与「地址写错了」分不开

`NOT_IMPLEMENTED` 是空字典 → 任何未登记路径都返回 404 `not_found`，
`not_implemented()` 根本不可达。现在登记了 `/battle/summary`（复盘摘要确实没做），
它回 **501 not_implemented**；真的不存在的路径才是 404。

### 3.6 页面白屏两个坑（这次做新页面踩的）

- 服务器的浏览器模块图只从 `app.js` 出发 → 第二个页面的入口脚本 404、整页一行 JS 都不跑；
- HTML 里的资源路径按**磁盘位置**写，而浏览器按**页面 URL** 解析
  （三个页面的短路径都在根上，所以相对路径只在平铺时碰巧能用）。

两条都改掉了，并加了契约测试：**每个页面按浏览器规则解析出来的每个资源都必须 200**。

## 4. G02 阵容模型：按你给的门槛判定

你给的部署门槛是：**未见家族上优于规则分且校准合理；否则 `evaluate_team` 继续用规则评分。**

数据结构与脚本已落地（`scripts/roco/build-team-dataset.py` + `train-team-model.py`），
按**阵容家族**切分（不是按行随机），逻辑回归是自己实现的纯标准库版本 ——
不引入新依赖。判定结果与结论写在：

```
reports/roco/g02-team/model-report.json
```

**判定结果：`passed = false` —— `evaluate_team` 继续使用规则评分，模型不接入任何对玩家可见的结论。**

| 门槛 | 判定 | 数值 |
|---|---|---|
| 未见家族上 log loss 优于规则分 | ✅ | 模型 0.6704 vs 规则分 0.6808 |
| 未见家族上 Brier 优于规则分 | ✅ | 模型 0.2392 vs 规则分 0.2438 |
| 校准合理（ECE ≤ 0.05） | ❌ | **0.1098** |

**两好一坏，按约定就是不过。** 而且理由是实打实的：
**AUC 只有 0.59（接近随机）**，测试集上最后那个校准箱里模型说「62% 会赢」、
那 30 局**全赢** —— 预测与实际反向。这种模型不该接到玩家看得见的结论上。

数据本身也说明问题：A 组 6 只 → 家族空间上限 **360**，
测试集只有 72 个家族 / 432 行。这个规模下 12 维特征学不出东西。
下一步该做的是**扩阵容池（6 → 12 只，家族空间 ×11）**，而不是换模型 ——
LightGBM 在 2000 行 12 维上只会更快过拟合，所以我**没有**为了对齐任务名去装它。

一句要单独说的话：这一轮**规则分赢了**，而且赢得公平 ——
我给规则分做了训练集上的 Platt 校准（它能得到的最好校准）才比的。
不做这一步的话模型会「大胜 0.61 log loss」，但那只是在比「规则分没校准」。
