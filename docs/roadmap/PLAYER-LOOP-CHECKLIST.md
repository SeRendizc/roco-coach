# 玩家闭环执行清单（P0-A…P2）

> 这份清单是**玩家闭环**的验收脊柱，跨 RC 存在。它与人 2026-09-22 给的补充计划一一对应。
> 建它的原因：RC 清单（`FLAGSHIP-V3-CHECKLIST.md`）回答的是「某个局部合同做完了吗」，
> 而**局部合同 DONE ≠ 玩家闭环 DONE** —— 这一页曾经在「工坊 42/42、UX 39/39、门禁 22/22」
> 全绿的情况下，玩家仍然选不了宠、点不动、看不懂（用户实测截图）。
>
> ## 打勾规则（缺一条都不许打勾）
>
> 1. **代码**在 `master` 上；
> 2. **真实页面操作**（不是单元测试、不是接口 curl）：桌面 1440×900 + 手机 390×844 各走一遍，
>    留截图或录屏，路径可复现；
> 3. **负向测试**：把这一条要防的坏情况注入进去，判据必须红（反证没命中也算失败）；
> 4. **release gate 更新后全绿**（`npm run verify:release`，含新判据所在的套件）。
>
> 另外三条纪律：
> - **规则证据**：官方规则没证实就标「候选 / 阻塞」，**不许编洛手规则**，也不许把
>   Demo 假设写成官方事实；
> - **支持度**：`622 图鉴 ≠ 622 完整可模拟`，未支持的效果**不得暗中按普通伤害结算**（fail closed）；
> - **不许刷内部指标**：门禁条数、覆盖百分比都不是完成标准，能玩到的闭环才是。
>
> 状态用：`未开始` / `进行中` / `阻塞(原因)` / `✅`（四条全满足才 ✅）。

### C3-a 的定位证据（2026-09-22 第 117 轮，实测，先记录再动手）

**两套词表冲突**，`effect_support` 是**一刀切**的旧标记，不是逐技能判定：

| 冻结数据 `skills.json` 的 `effect_support` | `coverage.py` 算出的档位 | 技能数 |
|---|---|---|
| `unsupported` | `SIMULATABLE_UNVERIFIED` | **501** |
| `unsupported` | `KNOWLEDGE_ONLY` | 71 |
| `unsupported` | `PARTIAL` | 7 |
| `supported` | 任意档 | **0** |

也就是说：**579 个进覆盖统计的技能里，`effect_support` 全是 `unsupported`** —— 连
「仙人掌刺击：对敌方精灵造成物理伤害。」这种纯伤害技能也是。而 `src/roco_env/service.py`
的技能查询闸门读的正是这个字段（第 725 / 774 / 1241 行），于是一律报
「效果原语尚未核验/实现（skills.json 的 effect_support = unsupported）」——
**说不清到底是「引擎算不了」还是「只是没登记」**。这正是人类说的那条风险的温床：
「未支持的效果不得暗中按普通伤害结算」需要**一个可信的档位来源**才谈得上判据。

**下一步（不该盲目改引擎）**：把「支持度」的唯一事实源定为 `coverage.py` 的计算结果
（它按描述能读出多少 + 引擎有没有对应原语），`service.py` 的闸门改读它；
`skills.json` 的 `effect_support` 降级为「冻结层的历史字段」，并在 manifest 里注明它不代表逐技能判定。
改完才写得出 C3 的判据（「档位 ↔ 引擎真的会不会结算」一致；不一致必须红）。
