## 1. 三级导航（按人类定义）

| 级 | 页面 | 职责 | 现状 |

## 2. 数据现实（这决定培养页能说什么、不能说什么）

`data/roco/owned/owned-pets.json` 实测（48 个体）：

| 字段 | 实测 | 培养页怎么呈现 |
|---|---|---|
| `nature` / `talent` / `specialty` | **48/48 `value: null`**（`value_source` 为空） | **一律显示「未核验」**，不许显示加成、不许猜数值（`docs/roco/OWNED-PETS.md` 的 `growth_attribute_policy`：效果全 UNKNOWN ⇒ 阵容/养成评估**不得当加成**） |
| `bloodline` | **12/48 有值**（电/虫/地…）、36/48 null | 有值的如实显示（并标来源），无值的显示「未核验」 |
| `panel_stats` / `growth` | **48/48 null** | 不显示、不补 0 |

⇒ **培养页的第一版不能靠「数值成长」立住**（没有数据）。能立住的三件事是：
**① 换招/调序（真实、可被引擎验证）**、**② 个体与配招的对照**、**③ 小芽基于规则的解释**。

## 3. 培养页要做什么（按优先级，每条带判据与必红反证）

### P0-a 换招 / 调序（= PLAYER-LOOP-CHECKLIST 的 B5）
- **唯一基准**：引擎的 loadout（`support-matrix.json#candidate_moveset` baseline 12 + overlay 36 合并；
  见 `FLAGSHIP-V3-CHECKLIST.md` 的 RC-203 行与 `/tmp/roco-moveset-research/REPORT.md`）。**等「配招核验」子任务结论落地后再接线**，否则就是「换了一套、打的是另一套」。
- **技术通道（已探明，只差接线）**：`env.py:156/231`、`service.py:1728-1741`、`src/coach/roco-client.js:932-939` 都已经收 `loadouts`；
  **唯一断点**是 `src/server/roco-service.js` 的 `client.battleNew({...})` 没把它传下去。
- **合法性由引擎判**（`rs.is_learnable`）：服务端**不许**自造一套可学表（`roster-48.json` 那 2/48 漂移就是这么来的）。
- 判据：① 换招后开局，引擎给的 loadout 与页面显示**逐位一致**；② 非法技能/非法顺序**被引擎拒**且页面如实显示原因；
  ③ 调序有机械后果（技能位/传动）；反证：把非法技能塞进去必须红、把顺序改成引擎不接受却仍放行必须红。

### P0-b 我的个体一览 + 详情
复用盒子页（RC-205）已有的 `GET /api/roco/box` 与比较能力；**不新造第二套数据源**。
判据：页面上每只的六维/属性/技能与 `/api/roco/box` 回执逐字一致；反证：写死一个样例数字必须红。

### P1-a 养成四项（诚实呈现）
按 §2 的表：null 就是「未核验」。**判据**：页面上不出现任何未登记的效果/加成数字；反证：给「性格」补一个 +10% 必须红。

### P1-b 资源成本预览（B3）
没有官方公式 ⇒ 一律标注「**Demo 假设**」，并写成可复算的一处配置。判据：文案不得写成官方公式；
反证：把假设写成「官方」必须红。

### P2 Coach「练哪只」+ 对六宠队伍的影响（B4）
`src/coach/coach-advice.js` 是纯规则建议层（文件头自己写着「页面还没接」）⇒ 培养页是它的天然出口。
**无证据时必须弃答**（不给结论、不给胜率、不给百分数）。判据：缺证据时返回弃答；反证：无证据给结论必须红。

## 4. 为什么这是 coach 的核心功能（人类那句话的落地）

1. **coach 能看到的配招 = 培养页决定的**：现在 owned 的四技能是伪随机抽样、实战用的是另一套（C6.76/C6.82），
   所以 coach 说的「这一手」和玩家练的那只**对不上**。换招打通后 coach 的解释才落在真配上。
2. **「练哪只」是玩家真问题**，而它现在**无数据可依**（§2）⇒ 培养页必须把「不知道」讲清楚，
   而不是给一个像结论的句子。这正是 README 里那条红线（未知 fail closed）在**产品层**的落点。
3. **培养页是 coach 的上下文入口**：个体、配招、练度（将来）都会进 `/api/roco/plan` 的公开面，
   coach 的建议质量取决于这里喂进去的东西。

## 5. 顺序（依赖链不能颠倒）

1. **配招核验 + 修好**（进行中）→ 定下「规范四技能 = 哪一份」；
2. **`loadouts` 接线**（一行 + 判据）→ 换招真的生效；
3. **培养页骨架**（`index.html` 改造：我的个体 + 换招 + PvP 入口）；
4. **三级导航**（L1→L2→L3 的入口/返回 + URL 可复现）；
5. **养成四项诚实呈现 + 成本预览**（P1）；
6. **`coach-advice.js` 接线 + 弃答判据**（P2）；
7. 三级导航的**页面判据重写**（现有 `roco-ux-acceptance` 39 条是按「营地=首页」写的，改造后要跟着改，
   判据口径**不许放松**：改的是读取点，不是标准）。

**并行注意**：`src/client/index.html` + `app.js` 是**一个写者**的活（改首页会牵动 `app.js` 的营地逻辑、
`style.css` 与 `mobile-sweep` 的 5 页扫描），要单开一轮做，别和 `roco.js`（战斗页）同时改。
