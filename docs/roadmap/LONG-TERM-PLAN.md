# 长期规划（2026-09-25 起）：从「游戏 demo」到「以 agent 为核心的教练系统」

> 人类口径（逐字，决定一切取舍）：
> ①「我希望模拟的是**600 只精灵、数据量很大、机制很复杂**的情况；**尽可能不要只依赖脚本计算和预制数据，更多依赖模型和 agent 本身**，
> 当然可以结合（RAG 等），但**重心在 agent 上，不在游戏系统**。」
> ②「所有 agent、coach、llm 的都是**重中之重**……一定都要**保质保量不能偷工减料**。」
> ③「养成关系到 **coach 的效果和 coach 需要解决的核心功能问题**，还是要做。」
> ④「响应速度要快，配队评估尽量 **3s 左右**出结果/建议。」⑤「无预算限制，但也不要浪费。」
>
> 三条**永不放松**的红线：**伤害与胜负永远由 Python 规则引擎算，LLM 只解释**；**不造胜率/概率/百分数**；**未知一律 fail closed**。

## 0. 北极星（一句话）

**玩家问任何关于这 600 只的问题，小芽都能靠「规则引擎的事实 + 自己检索/调用工具的能力 + 诚实的弃答」答出来，
并且每一句都带得起证据、每一局都跑得进 3 秒。**

衡量它的四个数（全部机器可算、可复算）：
| # | 指标 | 现在 | 目标 |
|---|---|---|---|
| M1 | 工具选择正确率（49 例预注册集，同批不调阈值） | **当前不可宣称**（见下方「口径更正 2026-09-27」）：预注册集现为 54 例、金标 59 条**全部 draft**、`gate_eligible:false`；历史基线 33/49 已不可复算 | ≥ 0.90（**解封的前提是把金标审完**） |
| M2 | 弃答正确率（该弃答时弃答 / 不该弃答时不弃） | 未建（RAG 有 1 条保留失败） | 建立并 ≥0.9 |

| M4 | 每条回答的可追溯率（数字/引用都被证据守住） | 服务端守卫已落地 | 100%（守卫拒绝即为 0） |

## 1. 六个阶段（每阶段都有可验证的完成判据）

### Phase A · 收口与冻结（进行中，1–2 天）

### Phase B · 培养页 + 三级导航（3–5 天）—— **coach 的数据入口**
- **做什么**：`index.html`（L1 培养页：我的一只 / 换招 / 养成四项如实呈现 / 成本预览 / 小芽建议）→ 点 PvP →
  L2 选配队（现 `roco.html` 选阵容）→ L3 战斗；**换招真的生效**（`src/server/roco-service.js` 补传 `loadouts`；
  合法性**交引擎 `is_learnable`**，Node 侧不许自造可学表）。
- **完成判据**：三级入口/返回真鼠标可走且 URL 可复现；换招后**页面显示 == 引擎 loadout 逐位**；非法换招被引擎拒且原因可见；
  养成四项 null 一律显示「未核验」、页面无未登记数字；三档宽度不溢出。
- **为什么在 agent 之前**：coach 看不到「玩家练的是哪只、配的是哪四招」，后面所有 agent 能力都会**打在错的靶子上**（C6.76/C6.84 的教训）。

### Phase E · 评测与证据体系（贯穿全程）
- **离线录制回放门禁**（已落地 4/4）：真模型响应录一次、之后每次门禁离线复验 ⇒ **不花钱、可复现**。

- **完成判据**：任何"能力提升"的说法都必须能指向**分布外**的留出集数字。

### Phase F · 旗舰交付（最后）
- **5 分钟 demo**（盒子 → 比较 → 锁定 → 补队 → 战斗 → 主动提示 → 展开取舍 → 局末教学 → 迁移验证）中缺的两段：
  **局末教学端到端**与**时间预算判据**。
- **面试报告**（需要人类给受众与口径）。
- **完成判据**：整条链路一次跑完 ≤5 分钟且每段有判据；报告里每个数字可复算。

## 口径更正（2026-09-27，全面复查之后）

这一节是**对人类 2026-09-26「逐条要么补上、要么在计划里明确降级（不许含糊）」**的直接回答。
凡本节与上文冲突，**以本节为准**。

### 一、M1（工具选择正确率）**当前不可宣称**

- **不可宣称的理由（三条，都能当场核）**：
  1. 预注册集**已经不是 49 例**：`reports/live-model-eval.json` 现为 **54 例**（`caseSetSize 54`）；
  2. 金标**没有审**：`data/roco/gold/review-state.json` 里 **59 条全部是 draft**、`reviewed_by` 全为 null；
  3. 闸门因此**没开**：`goldReview.approved = 0/59`、`gate_eligible:false`、`capabilityConclusive:false`。
- **同一份报告里两个数并存，看哪个都能自证**：分层判分 `toolSelectionCorrect = 54/54 = 1.000`
  （它**不过未审闸门**），严格判分 `toolSelectionCorrectnessRate = 0`（未审金标强制置假）。
  ⇒ 本计划**不再引用任何 M1 数值**，包括历史基线 `33/49`（它与现在的 54 例不是同一批）。
- **解封条件（写死，避免再来一次含糊）**：把 `data/roco/gold/review-state.json` 的 59 条审完
  （`approved = 59/59`）⇒ `gate_eligible:true` ⇒ 才能在**同一批**上重算 M1 并对外说数。
- **谁来做**：金标审核需要**人**（这是人类决策，不是我能代签的）。在审完之前，M1 一栏保持「当前不可宣称」。

### 一之二、C5 的第三处宽松：**明确降级为"已知且有界"**（2026-09-27）

计划 C5 写的是「收紧已记档的三处宽松：`1,2,3` 豁免 / 中文数字 / 白名单可借别处数字」。
前两处已收紧（见台账 §C6.310：`1/2/3` 免检已删、中文数字进同一条判据）。**第三处本轮决定降级**，理由是
"它比字面听起来窄得多"，而不是"做不了"：

- 守卫**已经做过的实体绑定**（`src/coach/runtime.js` 的三处，逐条都在）：
  ① **回合内的血量声明**必须对上**那一回合的 after 快照**（`after-hp-mismatch`），不是"包里任意一个血量"；
  ② **被取消的行动**不许被说成打出了伤害（`cancelled-action-claimed-as-hit`）；
  ③ **满豆/满能量**的声明必须对上**那一只当回合的能量**（`energy-not-full`）。
- **剩下的洞**：一句**没被上面三类绑定覆盖**的话，可以引用同包里**别处**的数字
  （例如把对手的速度说成自己的）。要彻底关掉它，需要一次**逐句实体绑定**（把每个数字绑到
  "哪一只 / 哪一回合 / 哪一条回执"），那是**与现有守卫同量级**的新工程，不是"再收紧一行"。
- **降级之后的承诺**：在逐句绑定做出来之前，**不对外宣称"数字 100% 可追溯"**；
  已覆盖的三类绑定照旧受判据保护（`tests/roco-server-side-guard.test.js`）。
- **重启条件**：什么时候做逐句绑定，什么时候把这一条从降级改回待办 —— 两件事绑在一起。

### 一之三、C2 / C3 / Phase E：**逐条明确降级**（2026-09-27）

计划里剩下的三条硬缺口，按人类「要么补上、要么明确降级（不许含糊）」逐条处理：

**C2 `assess_evidence`（够不够/要不要再查/该不该弃答）→ 降级为待办，且写明"为什么现在做不了"**
- 事实：全仓 **0 处实现**；检索步数上限仍是 `src/coach/runtime.js` 的 `limit=3` / `Math.min(4, limit)`；
  替代开关 `ROCO_COVERAGE_FORCE` **默认关**。
- 现在做不了的**可核理由**：它要判"证据够不够"，而**判据本身没有**——本仓至今没有"够/不够"的
  标注数据（金标 59 条 **全 draft**，见 M1 那条）。在标注到位之前实现它，只会得到又一个**无法证伪**的模块。
- **重启条件**：金标审完（`approved = 59/59`、`gate_eligible:true`）之后，用同一批数据先做
  "证据够不够"的标注切片，再谈实现。

**C3 的 M2（弃答率 / 弃答正确率）→ 同上，降级为待办**
- 事实：`src/`、`scripts/`、`reports/` 里**都没有**这两个指标（只有检索层的 `abstained`）。

  两者的重启条件**是同一条**。
- **降级之后的承诺**：在 M2 建起来之前，本计划**不引用任何"弃答"相关的比率**，
  也不把"不知道"说成已经在指标里管起来了。

**Phase E（困难类留出集）→ 部分存在，明确写清"有多少、够不够、缺什么"**
- **已存在的**：`tests/evals/agent-tasks-v2-tool-coverage.jsonl` —— **20 条**（10 个工具 × 正/负各一），
  带三条机器判据：参数逐条过 `validToolArgs`、按模板切分、**与训练数据零重叠**（问句逐字不同）。
- **为什么还不够**：20 条只够**发现"完全没考过"**（v1–v7 的 8 个工具正例 0/10 就是这么发现的），
  不够报**泛化**；而且它覆盖的是"工具选择"，**不是**"困难类别"（多轮、冲突回执、长上下文、模糊指代）。
- **重启条件（写死，不靠自觉）**：① 每个困难类别**≥30 条**且与训练集**零重叠**（判据已现成，扩数据即可生效）；
  ② 扩完之后**先跑基座**看基线，再谈"提升"。在那之前，**任何拿这 20 条算出来的比率都只当"冒烟"**。

### 二、RC-902（配队解释 3 秒增量段）**本轮决定不做**

- **事实**：`src/coach/team-serving.mjs` 与 `src/server/roco-service.js` 里 `explain` **零命中**；
  `roco-service.js` 全文 **0 处** `runCoach`/`complete(`/`provider` ⇒ **配队链至今完全不调模型**。
- **为什么不做（而不是"待开工"）**：
  1. 它要的是"3 秒预算里塞一段 LLM 解释"，而**分段延迟至今拿不到**
     （`reports/roco/agent-metrics.json` 的 `latency.segments = null`，理由逐字
     "per-phase latency is not separable from outside the server"）⇒ **无法判据化**；
  2. 没有**困难留出集**（Phase E 至今空缺）⇒ 做出来也**无法证明它比模板好**，只能自说自话；
  3. 现有 `team-serving.mjs` 的两段（`plan` + `evidence_and_counterfactual`）已经在 3 秒内出结果，
     **没有证据表明加一段模型解释会让玩家更满意**。
- **降级之后的承诺**：M3（LLM 段 ≤3s、首屏不依赖模型）**不再挂在 RC-902 上**；
  若将来要重启它，前置条件是**先有可分段计量的产物**与**困难留出集**，两条都写在这里。
