# Agent / LLM 能力真正提升方案（2026-10-17 · 针对周宇宸当前阶段）

> 目标不是"再多学几个名词"，而是在 8 周内让你能在面试里**独立改代码、预测边界、自己评测**，
> 并且把"模型服务/推理"这块从简历关键词变成能讲出数字的实操。方案默认：每天 90 分钟，
> 一周 5 天，另加周末 2 小时复盘；**所有练习都落在你已有的仓库上**（roco-coach、agent-runtime-lab、
> agent-eval-lab、decoder-inference-lab），不新开玩具项目。

## 0. 先诊断：你现在的真实水平与缺口

**已经很强的**：
- 能把一个真实业务（游戏 Coach Agent）从产品需求推到实现、验收、复盘（Roco Coach，公开仓库可查）。
- 知道"规则/模型分工""信息边界""过期建议""grounded 校验"这些**一线 Agent 工程概念**，而且有代码。
- 有华为 AI Arena 多 Agent 竞赛的团队成绩与表达经验。

**最致命的缺口**（上一轮独立评审原话）：
> "能说明产品愿景，但无法沿真实请求定位到代码、预测边界行为、独立修改。"

翻译成可训练的三种能力：
1. **trace 能力**：给一条真实请求，10 分钟内指出它经过的文件、状态变化、失败点；
2. **predict 能力**：改一个参数/删一个分支，能预判哪条测试会红、线上会出现什么现象；
3. **modify 能力**：从"提假设 → 写最小补丁 → 先让反例红 → 再让它绿"完整走一遍。

**第二层缺口（投模型服务岗时会被问）**：推理系统实操（KV cache、continuous batching、p50/p95、
首 token 延迟、显存/吞吐权衡）目前只有概念，没有亲手跑出来的数字。

## 1. 训练方法：三个闭环，缺一不可

### 闭环 A：Build → Eval → Explain（每周一个）
- **Build**：改一处真实逻辑（不是加页面）。
- **Eval**：先写会红的判据，再让实现变绿；保留失败日志。
- **Explain**：用 150 字写"我原来以为 / 实测 / 根因 / 改法"，存进 `docs/GROWTH-LOG.md`。
> 检验标准：**没有 eval 的 build 不算完成；没有 explain 的 eval 不算学会。**

### 闭环 B：读一篇 → 复现一个最小实验（每两周一个）
- 只读能落到代码的论文：ReAct、Toolformer、DPO、PPO/GRPO、GAE、RAG 评测、τ-bench。
- 复现**最小可信版本**：例如 30 行 GAE、100 行 DPO loss、一个 50 条检索评测集。
- 结论必须写成"在我的实验里有效/无效"，不许写"论文说有效"。

### 闭环 C：面试驱动（每周两次，每次 30 分钟）
- 抽 3 个问题，**合上资料讲 90 秒**，录音；对照 `docs/interview/SECOND-ROUND-PACK-2026-10-17.md` 查漏。
- 每两周做一次"代码面试"：从 repo 随机挑一个函数，让对方（或 AI）问"改成 X 会怎样"，
  你现场定位 + 预测 + 给出改动点。

## 2. 八周路线图（每周产出物都可面试引用）

| 周 | 主题 | 具体动作 | 可验证产出 |
|---|---|---|---|
| 1 | **请求 trace + 边界预测** | 把 Roco 的一条真实请求完整走查（8 跳），为每跳写"失败会怎样"；挑 3 个"改这里会怎样红"并实际跑红 | `docs/interview/CODE-TRACE-2026-10-17.md`（已产出）+ 3 条自己跑出的红日志 |
| 2 | **Agent harness 最小实现** | 在 agent-runtime-lab 写一个 300 行以内的 agent loop：3 个工具、预算、stale 失效、grounded guard；配 20 条任务评测 | 一个能复跑的评测脚本 + 失败类型分布（不是通过率一个数） |
| 3 | **RAG 评测与负结果** | 复用 `reports/retrieval-extended.*`：补 Recall@k、MRR、bootstrap CI、McNemar；再试 1 个新检索器（BM25+embedding+rerank），**允许它输** | 一页实验报告：四臂数字 + 显著性 + 为什么保留/不保留 |
| 4 | **推理服务实操（一）** | Mac 上跑 vLLM 或 llama.cpp：测同一 prompt 的 p50/p95、首 token、吞吐；改 `max_tokens`/batch/quantization 各测一组 | 一张延迟-吞吐表 + 一段"为什么首 token 比总延迟更影响体感"的解释 |
| 5 | **SFT / 工具调用微调** | 用现有 4B 数据或公开 tool-use 数据，LoRA SFT 一个小模型；固定留出集，报告 before/after（含失败案例） | 训练日志 + 留出集分数 + "哪些变好、哪些变差" |
| 6 | **偏好优化 / RL 最小实验** | 写 100 行 DPO 或 GRPO（可以是 toy），用同一留出集对比 SFT；搞清楚 KL、advantage、信用分配 | 一份"RL 更新了什么、没更新什么"的 300 字说明 + 曲线 |
| 7 | **生产化** | 在 Roco 上做：答案缓存命中率、fallback 率、超时/取消、成本估算、来源标注；做一次 A/B（local vs cloud） | 一页 cost/latency/fallback 看板；能解释每个数字的分母 |
| 8 | **收口与表达** | 把 8 周产出压成 6 个故事：trace、改一条规则、RAG 负结果、推理服务、微调、失败复盘；模拟面试 3 次 | 6 段各 90 秒的口述稿 + 面试官追问清单 |

> 时间不够就砍周 5/6 的深度，**不能砍周 1/2/3**——那是面试官区分"AI 协作"与"本人能力"的地方。

## 3. 每日 90 分钟的标准动作（照做即可）

1. **20 分钟读**：只读今天要改的那段代码 + 对应测试（不读教程）。
2. **40 分钟写**：先写一条会红的判据 → 改实现 → 跑到绿；失败也保留。
3. **15 分钟记**：`docs/GROWTH-LOG.md` 写 4 行（假设/实测/根因/下一步）。
4. **15 分钟讲**：合上资料，用 90 秒把今天做的事讲给手机录音；讲不清 = 没学会。

**每周复盘 30 分钟**：这周有几条判据是我自己写的？有几条是我预测对的？被追问时卡在哪？

## 4. 具体资源（少而精，按顺序）

**Agent 工程**
- Anthropic《Building effective agents》（工具/工作流/agent 的边界）
- ReAct（arXiv:2210.03629）+ τ-bench（arXiv:2406.12045，工具-用户交互评测）
- 你仓库里的 `src/coach/runtime.js` 与 `tests/evals/` —— **最好的教材是你自己项目的失败记录**

**RAG / 评测**
- 《Evaluating RAG》类综述 + BEIR（检索评测协议）
- 统计：McNemar 检验、bootstrap CI（你报告里已经用过，亲手推一遍）
- 负结果的价值：你已有四臂对照，把它写成"为什么最好的臂也不显著"

**RL / 后训练**
- Spinning Up（RL 基础）、GAE 论文、PPO、DPO（arXiv:2305.18290）、GRPO/DAPO 原论文
- 你的 `reports/tool-router-rl.json` 与 `reports/intervention.json`：把 1152 参数实验的
  "奖励怎么设、为什么这么小、边界在哪"讲成 3 分钟

**推理服务**
- vLLM 文档：PagedAttention / continuous batching
- 《Efficiently Scaling Transformer Inference》类博客；亲手测一次 p50/p95/首 token
- 你已有的 `decoder-inference-lab` 拿来做 KV cache 对比实验

## 5. 三个月后的验收标准（可自测）

- [ ] 任选 Roco 一条真实请求，**10 分钟内**画出链路并指出 3 个失败模式（不看文档）。
- [ ] 任选一个函数，改一个分支，**先说出**哪 2-3 条测试会红，再跑验证，命中率 ≥ 70%。
- [ ] 能独立写出一个 20 条任务的 agent 评测集，并解释为什么这 20 条不是"凑数"。
- [ ] 能讲清 RAG 四臂实验的**负结论**与统计口径，不吹"RAG 提升了效果"。
- [ ] 能跑出一次 vLLM/llama.cpp 的延迟-吞吐表，并解释首 token 与 batch 的权衡。
- [ ] 能区分 SFT / DPO / 在线 RL 各自更新什么、奖励从哪来、什么不能声称。
- [ ] 面试模拟中，被追问"你本人做了什么"时，能给出**一条自己改的代码 + 一条自己跑红的测试**。

## 6. 不要做的事（比做什么更重要）

1. **不要再堆功能/页面/宠物数量**。项目已经不缺规模，缺的是"你能独立动的那一小块"。
2. **不要用"AI 协作"解释一切**。面试官不反对 AI 协作，反对的是"你讲不清哪一行是你决定的"。
3. **不要报没有分母的通过率**。任何指标先问：分母是什么、失败/超时算不算、样本多大。
4. **不要收藏教程**。每天只读今天要改的那段代码；读不完的存进清单，周末统一删。
5. **不要把"跑通 demo"当能力**。跑通是产品验收，能力验收是"改坏了能修、换环境能跑、被追问能答"。
