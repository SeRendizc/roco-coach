# RC-403 Support Classifier v2：一只精灵到底能不能模拟

> 模块：`roco/src/roco_env/support.py`（`python3 -m roco_env.support`）
> 报告：`reports/roco/rc403/support-classification.json`（622 只，逐只给部件明细）
> 守卫：`roco/tests/test_support_classifier.py`（7 条，含 2 条必红方向）

## 为什么需要它

到上一轮为止，仓库里有两份**零散**的事实：`build_support_of()` 说配招是冻结的还是按需推算的
（RC-402），`coverage.py` 说每条技能/特性支持到什么程度（RC-401）。但产品与训练数据要问的是
**第三件事**：**这一只精灵**能不能上场、上场之后有多少行为是真的在按规则走。

把「能上场」当成「能模拟」是这一轮最容易犯的错：一只按需推算配招的精灵能打，但它的**特性**
大概率没有实现——**239/245 条特性连登记都没有**（`traits.py` 只登记 12 条）。那意味着它在场上
的行为跟真实游戏不一样。

## 判据：按**部件**定档，精灵档描述「作为一只可上场的单位，有多少行为真的按规则走」

部件 = 配招来源 + 特性 + 四个技能，各自取支持等级，然后：

| 精灵档 | 条件 |
|---|---|
| `KNOWLEDGE_ONLY` | **不能上场**（配招来源没登记） |
| `FULL_VERIFIED` | 能上场，且**每一个部件**都是已核验 |
| `SIMULATABLE_UNVERIFIED` | 能上场，且每个部件至少「会结算」（没有未实现的） |
| `PARTIAL` | 能上场，但有部件**根本没在按规则走** |

另外两个清单必须分开（否则会出现「说全可模拟却列着未核验部件」这种自相矛盾）：

- `unverified_pieces`：结算了、但没有一手/实机证据；
- `unsimulated_pieces`：**根本没在按规则走**（PARTIAL / KNOWLEDGE_ONLY / REFUSED）；
- `refused_pieces`：明确拒绝实现的部件（缺一手证据，理由在 `traits.py`）。

**刻意不用「最坏件」规则**：239/245 条特性没登记，最坏件会把 599 只**明明能上场、
四个技能也都能结算**的精灵判成 `KNOWLEDGE_ONLY`（「只有资料」）——那句话是错的。

## 实测（622 只）

| 档位 | 只数 |
|---|---|
| `FULL_VERIFIED` | **0** |
| `SIMULATABLE_UNVERIFIED` | **8**（护主犬 / 音速犬 / 海豹战士 / 号儿鱼 / 画间沉铁兽 / 热团团 / 焰米龙 / 月辉鹭） |
| `PARTIAL` | **614** |
| `KNOWLEDGE_ONLY` | 0（RC-402 之后 622 只都能上场） |
| `REFUSED`（精灵档） | 0（被拒的是**部件**，不是整只） |

卡点统计：**特性 609 只**、配招里的技能 150 只；12 只带 `refused_pieces`
（例如「不朽」`skill_000129` 落在寂灭骨龙/大头骨龙，「化蝶」的 `skill_000104` 落在三只形态上）。

## 这份报告怎么用

- **页面**：候选卡/详情可以如实写「能上场 · 特性未实现」而不是笼统的「支持」；
- **训练数据生成器**：只有 `SIMULATABLE_UNVERIFIED` 与 `FULL_VERIFIED` 的精灵才适合当标签来源，
  `PARTIAL` 的必须把「哪些部件没实现」写进 manifest（否则学到的行为差异会被当成策略差异）；
- **下一批实现顺序**：609 只卡在特性上 ⇒ 特性层的登记（RC-401 的下一批）覆盖收益最高。

## 如实边界

- 档位只回答「引擎会不会结算」，**不回答机制对不对**（那要靠实机 microcase）；
- 连击能力按参数假定（默认按候选配置的声明），换口径要重新生成；
- `FULL_VERIFIED` 目前为 0 是**真实状态**，不是判据坏了：特性层的实机证据不足；
- 接口（`/rules/query` 的 roster）本轮**没有**改动——那条回执被已录制、禁止重跑的 agent 轨迹
  钉着，加字段会让它们全部对不上；要给页面用，走本报告或新端点。
