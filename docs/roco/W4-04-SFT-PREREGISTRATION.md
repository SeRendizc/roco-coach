# W4-04 预注册：SFT 适配器评测（v4 与**重测** v1/v2/v3/基座）

**这份文件在跑之前就写好。** 它的作用只有一个：把判据先钉死，免得看到结果之后再决定
什么算「变好了」。如果下面的判据在跑完之后被改动，必须**显式**留痕并说明为什么。

## 0. 为什么还要重测一遍已有的版本

第 37 轮做归档检查时发现了一件必须先说清楚的事：

**模型臂的成绩存档错了位，而没有任何检查发现过。**

`shadow-replay` 原来的报告里只有 `arm` / `gateway` / `prompt_digest`，
**没有「这份结果是哪个适配器产出的」**；而运行器每次把结果写到同一个
`reports/roco/shadow-replay-local_4b.json`，再由人工 `cp` 成 `-sft-vN.json`。
逐次比对 git 历史之后的实际情况是：

| 文件 | 现在装的是什么 | 应该装的是什么 |
|---|---|---|
| `shadow-replay-sft-v2.json` | **v1 的成绩**（229/288） | v2 |
| `shadow-replay-sft-v3.json` | **v2 的成绩**（268/288） | v3 |
| `shadow-replay-local_4b.json` | 最后一次跑的那个（v2，268/288） | 基座 |
| v3 的真实成绩（文档写 205/288 = 0.7118） | **一个产物都没留下** | v3 |

也就是说：文档里那张「v2 最好 0.9306 / v3 比基座还差 0.7118」的表，
**只有 v1 和 v2 的数字有产物支持，v3 的数字没有任何产物**；
而「基座 225/288」来自 `local_4b.json` 在 `57fe5f3` 那一版，之后被覆盖了。

**处置**：不靠猜名字修存档。把 base / v1 / v2 / v3 / v4 **在同一套协议下重测**，
每份报告带**模型身份**（模型路径 + 适配器路径 + 权重文件 sha256 + 提示摘要），
并用显式 `--out` 写到自己那个名字上。旧的那几个错位文件挪进
`reports/roco/invalidated/`，并在那里写明它们为什么不可用。

同时做了根因修复（否则还会再错一次）：

1. 报告新增 `identity`（模型 / 适配器 / `adapter_sha256` / `prompt_digest` / `identity_digest`）；
2. `shadow-replay` 支持 `--out`，存档名不再由 arm 名推导；
3. `stop-mac.sh` 原来找的是**从来没被写过**的 `serve.pid`，于是「停网关」永远是个空操作
   —— 这正是「换适配器时以为换了、其实没换」的上游原因，已改成认 `gateway.pid` 并按端口兜底；
4. 新增守卫：`-sft-vN.json` 里记的 `adapter_basename` 必须以 `vN` 结尾，
   基座报告必须 `adapter == null`（见 `tests/evals/roco/model-arm-identity.test.js`）。

## 1. 协议（每个 arm 逐字相同）

```bash
bash scripts/model/stop-mac.sh                                   # 必须真的停掉（见上面第 3 条）
ROCO_LOCAL_ADAPTER=<adapter 或空> bash scripts/model/start-mac.sh
curl -sS http://127.0.0.1:8766/healthz                           # 记录 adapter 路径
node scripts/roco/shadow-replay.mjs --arm local_4b \
  --out reports/roco/shadow-replay-<label>.json \
  --compare reports/roco/shadow-replay.json                      # 对规则臂（288/288）
```

- 基准：**规则臂** `reports/roco/shadow-replay.json`（288/288）。所有 arm 与它逐任务配对。
- 尺子：`tests/evals/agent-tasks-v1.jsonl` 的 **288 条任务**，同一世界（`worldsFor(..., 1)`）、
  同一判定器（`checkTask`）、同一提示（`prompt_digest` 必须一致）。
- 模型只负责**选工具**；参数照常过 `validToolArgs` 与真实引擎；状态版本由运行时覆盖。
- 每条命令的输出都留档，报告里的 `identity` 必须与文件名一致。

**这一套不因为「上次跑出来是多少」而调整。** 重测出来的数字如果与文档不符，
改的是文档，不是重测。

## 2. 预注册判据（v4）

v4 的数据：1,752 条（train 1,395 / val 306 / test 51），每任务 9 个世界，
切分 `strict`（留出机制 `轮次推进` / `拒绝`）；配置与 v1—v3 相同（LoRA r=8、8 层、
900 iters、lr 1e-5、mask-prompt、seed 20260921）。

| # | 判据 | 阈值 | 为什么是这个阈值 |
|---|---|---|---|
| P1 | **总体通过率** | ≥ **重测后的 v2** | v4 的主要变量是**数据量**（1,395 vs v2 的 552）。如果数据量翻两倍多还不能不劣于 v2，那说明瓶颈不是数据量，这条路要重新想 |
| P2 | **`roster_constraint`** | ≥ v2 | v3 之后分析出的主缺口就是这一类（v2 是 8/24）。它现在每任务能选到 9 个世界，是**数据量假设的直接检验** |
| P3 | **`rules_lookup`** | ≥ v2 | 最大的一类（72 条），且是「会不会选对工具+参数」的主战场 |
| P4 | `invalid-arguments` | ≤ 5 | v2 已经是 0；这一条是**回归护栏**，不是目标 |
| P5 | **延迟** | p50 ≤ 700 ms 且 p95 ≤ 1500 ms | 游戏内那条路径要在 ~3 s 内出结果；这是**可用性下限**，不是性能目标 |
| P6 | **family 外指标** | `by_split.family.held_out.pass_rate` ≥ 0.85 | 「换一个阵容家族还灵不灵」。这条与 P1 分开看：总体通过率可以把泛化差掩盖掉 |
| P7 | **逐任务配对** | 相对 v2 的退化条数 ≤ 扳回条数 | 只看总数会掩盖「这边修好 20 条、那边坏 20 条」。配对差异必须同号 |
| P8 | **回滚开关** | `ROCO_LOCAL_MODEL` 默认 `off`，且 `off` 下本地模型进程**一次都不被启动** | 模型类交付必须能一键退回规则臂；开关状态要写进报告 |

> **订正（2026-09-21，跑之前发现）**：P8 原来写的是 `ROCO_LOCAL_MODEL_MODE`，
> 那是**错的变量名**——代码里读的是 `ROCO_LOCAL_MODEL`（`src/coach/local-model.js`）。
> 判据本身没变，只是名字写错了；如果按错名字去检查，会得出「开关不存在」的假结论。

**判定规则（先写死）**：

- P1—P4 与 P7 **全部满足** → 「可进入下一阶段（真实链路 `shadow` 档观察）」；
- 任一条不满足 → 记为**负结论**，保留产物与适配器，不进入下一阶段；
- P5—P6 不满足也**不阻止**记录结果，但不允许在报告里把它写成「可上线」；
- 无论结果如何，**通过率都不得被称为胜率**，也不得据此声称真人效果。

## 3. 明确「校准」在这一项上不适用

goal 要求每个模型类交付都给校准。对**工具选择**这一项，校准**没有定义**：
模型输出的是一个离散的工具名（或 `stop`），没有一个可校准的标量概率，
而判定器给的也是 0/1。硬要说「置信度」只能拿生成时的 token 对数概率去凑，
那既不是这个模型的训练目标，也没有任何下游决策会用它。

所以这里如实写：**校准不适用于本项**，不给数字。
需要校准的是 **W5-04 的介入模型**（它输出概率、并且真的用一个阈值在做抑制决策），
那一项的校准（ECE）在 `docs/roco/W5-04-INTERVENTION-GATE-V2.md` 里有实测值。

**不许为了填表格编一个校准数字。** 不适用的项写「不适用」也是一种结论。

## 4. 与评测集的关系（不要把总体通过率读成泛化）

288 条任务门禁**包含** train/val/test 三侧的任务。所以：

- 它是**同一把尺子**（base/v1/v2/v3/v4 都量同一套），适合做**横向比较**；
- 它**不是**留出评测。训练侧见过的机制/模板上得分高，只说明记住了。
  真正回答泛化的是 P6 的 `by_split.*.held_out` 切片，两者必须一起报。
- SFT 数据自己的 test 侧（51 条）**全部目标是 `{stop:true}`**（留出的两个机制恰好都是
  「该停」的情形）。所以那一侧**不能**用来衡量工具选择能力——这一点由
  `scripts/roco/verify-sft-split.mjs` 的 `targets_by_side` 报出来，写在这里免得被误用。

## 5. 不声称

- 不声称 4B 做不到这些任务：只说明**当前提示 + 当前数据**下它在这 288 条上的表现；
- 不声称这是真人对话分布：任务集是构造的，局面由引擎按固定 seed 生成；
- 不把模型分数叫胜率（这里没有胜负，只有判据过没过）；
- 不声称 SFT 之后「Agent 变强了」：只说明**工具选择**这一环的判据通过率；
- 不声称 v1—v3 的旧文档数字正确——它们正在被本次重测替换。

### 6.3 仍然不声称

- 288 条门禁**不是留出评测**（见 §4）。v4 的 0.9549 是「同一把尺子上的横向比较」，
  不是「泛化到新家族」——那要看 P6 的 0.9271，而它也只是**这套构造任务**上的家族外切片。
- v4 现在是**最好的适配器**，但它**还没有接进默认链路**：
  `ROCO_LOCAL_MODEL` 默认 `off`，页面走的仍然是规则臂。
- 仍然没有真人盲评、没有游戏内实测；通过率不是胜率，也不是玩家满意度。

### 6.4 一个必须一起报的事实：1,395 行里只有 474 条**不同的题**

写 `verify-sft-split.mjs` 时报出来的（`duplicates` 字段，不判红但必须说）：

| 文件 | 行数 | **不同提示数** | 重复行 | 最大重复 |
|---|---|---|---|---|
| `train.jsonl` | 1,395 | **474** | 921（66%） | 9 |
| `valid.jsonl` | 306 | 110 | 196（64%） | 9 |
| `test.jsonl` | 51 | 36 | 15 | 2 |

原因很清楚：每个任务配 9 个世界，而提示里只带 `message` + `state_version` +
（有才带的）`locked_pet` / `team`。6 个 `camp-*` 世界对同一个任务给出**完全相同**的提示，
只有状态版本不同的对局世界才会分叉。

**所以「数据从 552 行涨到 1,395 行」不等于「信息量涨了 2.5 倍」**——
`train` 侧真正不同的题是 **474 条**（v2 那一版是 4 个世界，按同样的口径只会更少）。
v4 相对 v2 的提升（268→275）与这个口径是一致的：**加世界确实加了行数，但重复的
提示带来的只是权重，不是新的知识。** 下一步要真把数据做大，得让**每个世界真的
改变提示内容**（例如带出该世界特有的公开事实），而不是继续加同质局面。

这一条也解释了为什么 `roster_constraint`（8→13/24）是这轮提升最大的一块：
它正好是被 6 个同质 `camp` 世界覆盖得最少、而新增的对局/条件世界能真正改变题面的那一类。
