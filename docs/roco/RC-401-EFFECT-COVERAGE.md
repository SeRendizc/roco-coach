# RC-401 效果覆盖台账 + 第一条按覆盖收益迁移的原语（连击）

> 台账模块：`roco/src/roco_env/coverage.py`（`python3 -m roco_env.coverage`）
> 报告：`reports/roco/rc401/effect-coverage.json`
> 守卫：`roco/tests/test_effect_coverage.py`（5 条）、`roco/tests/test_multi_hit.py`（7 条）

## 为什么先做「尺子」

RC-401 的施工口径是「**按覆盖收益**增量迁移效果原语，不一次重写 68 个」。但在这之前，
仓库里**没有任何地方**回答「现在能跑多少、下一条该实现哪个」：`skills.json` 里 824 条记录的
`effect_support` 一律写着 `unsupported`（导入期的保守标注），而 `traits.py` 只登记了 12 条特性。

所以第一条交付是**覆盖台账**：拿 `parse.parse_skill` 逐条跑 579 条战斗技能，拿 `traits.TRAITS`
的登记状态给 245 条特性定档，并把「解析不出来的原因」按频次排序——那就是下一步的依据。

### 四档（沿用 RC-403 的词汇）

| 档位 | 含义 |
|---|---|
| `FULL_VERIFIED` | 有实现且有一手/实机证据（目前只有 6 条特性走 `traits.py` 的 FULL） |
| `SIMULATABLE_UNVERIFIED` | 描述被完整读出且引擎会结算（**不等于**实机核验过） |
| `PARTIAL` | 读出一部分，仍有没认领的机制片段（引擎**不做部分应用**，如实登记） |
| `KNOWLEDGE_ONLY` | 只有文字资料，引擎不会结算 |
| `REFUSED` | 明确拒绝实现（缺一手证据，理由写在 `traits.py`） |

### 关键口径：覆盖率是「数据 × 已声明能力」的属性

同一份数据，**legacy 口径与候选口径的覆盖率本来就不同**。台账因此把「已声明能力」显式带出来：

| 口径 | 可模拟实体 | 战斗技能可模拟 | 说明 |
|---|---|---|---|
| 未声明连击（legacy / v2） | 473 / 824（57.4%） | 467 | 连击一律算未实现 |
| 声明连击（`mobile_s4_candidate_v3`） | **507 / 824（61.5%）** | **513** | 静态连击被结算，动态连击仍算未实现 |

## 第一条原语：连击（multi-hit）

**为什么是它**：579 条战斗技能里 **67 条** desc 含「连击」，是除「特性未登记」之外频次最高的
未实现机制。而在实现它之前，`effects.py` 的伤害公式虽然**有** `hit_count` 参数，却**永远传 1**
——那 67 条技能被静默地按单次结算（这正是这个仓库最不允许的那种缺陷）。

**做法**（三条纪律）：

1. **静态读得出才结算**：`(\d+)\s*连击` → `Parsed.hit_count`；`1连击` 就是 1，`3连击` 就是 3。
2. **动态绝不猜**：`连击数+1` / `连击数永久+1` / `连击数翻倍` / `变为3连击` 一律进 `unparsed`，
   如实登记为未实现——它们的取值依赖印记层数/应对结果/使用次数，没有一手证据。
   静态基数仍可用（例如「1连击，敌方每有1层星陨印记，连击数+1」按 1 次结算 + 那条加成登记）。
3. **只有配置声明了能力才生效**：`damage.multi_hit`（`mobile_s4_candidate_v3` 声明，
   legacy / v2 **没有这一块**）。没声明 ⇒ 恒定 1 次，且「连击」照旧留在 `unparsed` 里被登记
   ——**legacy 逐位不变就来自这里**（8 条 golden 指纹全绿）。

结算后：伤害事件带 `hits: N`、日志写「（N 连击）」；这两处**只在 `hits > 1` 时**出现，
所以 legacy 的事件与日志一个字节都没动。

## 实测

| 项 | 值 |
|---|---|
| 静态连击技能被结算 | 46 条（67 条含连击 − 21 条另有未认领片段/纯动态） |
| 3 连击伤害 | 19 → **57**（正好 3 倍，确定性） |
| legacy 同技能 | 19（未声明能力，不变） |
| Python 测试 | 371 → **383 条 OK**（新增 5 条台账 + 7 条连击判据） |

## 如实边界

- `SIMULATABLE_UNVERIFIED` 只是「描述被完整读出且引擎会结算」，**不是**实机核验；
  伤害公式本身是社区假设（`effects.py::_community_v1`，非官方）。
- 连击的**逐次结算语义**（每次是否单独触发附带效果、暴击/取整是否逐次）没有证据，
  当前按「单次伤害 × N」处理，属于 `ENGINE_HYPOTHESIS`。
- 台账的收益排序粒度到「原语」，不是到具体句子；特性那 233 条「未被登记」也需要逐条定档。
- 下一步按同一把尺子排序：**选择（20）→ 传动（13）→ 随机（11）**，以及把 233 条未登记特性
  按「实现成本 × 覆盖收益」分批登记。

## 批四：吸血 / 过量回复转化 + `贪得无厌`、`渴求`（2026-09-23）

计划里说 `贪得无厌`「需要伤害后钩子」。实现下来更省的切法是**把两条机制做成引擎原语**：
`PetState.sustain`（`{"lifesteal_pct", "overheal": {...}}`）+ `env._settle_sustain`（造成伤害后结算），
特性只负责在入场时把**解析出来的**参数写进去 —— 引擎里结算的地方只有一处，
特性不该各写一遍数值（两条特性按**解析结果**分派，不按特性名）。

- 解析器补齐两条词法：`获得N%吸血` → `self_lifesteal`、`每过量回复N%生命转化为M%属性` → `overheal_to_stat`；
  **并修掉一个真的读错**：旧实现把「每过量回复5%生命转化为…」读成一次 `heal 5%`（实测复现），
  那会让引擎把「转化规则」当成本体回血。
- 两条假设如实登记（数据没写）：溢出的**累计口径**（按多次回复累加、满档才转化，而不是每次各自取整）
  与转化出来的增益**持续到本局结束**；结算时写进 `state.unsupported`，事件里也带出 `carry_pct`。
- `渴求`（恶魔叮/叮叮恶魔）只吸血、不转化 → 同一段实现，登记为 **FULL**（数值全部可机械读出）。

# 批次五（第 30 轮）：台账里「说不出原因」的那些条目 —— 匿名桶 174 → 0

## 为什么要做这一批（不是"好看"，是工作单看不见东西）

`coverage_ranking` 是"下一步做什么"的依据（按频次排序）。但这一批开工前它长这样：

```
 228 条 → 未被登记 （技能 0 / 特性 228）
 174 条 → （未命名） （技能 174 / 特性 0）      ← 匿名桶
  43 条 → 连击 / 20 条 → 选择 / 11 条 → 随机 …
```

那个 **174 条的匿名桶**里其实混着好几种机制（实测前 12 条就有「每次使用后本技能威力永久+45」
「回合结束时能耗永久-1」「应对状态：本次技能威力变为3倍」「若敌方能量≤2，造成5倍伤害」…），
但台账**只说"解析器认不出的机制"、不说是哪一段**，于是按频次排序的下一批工作单对它无能为力。

**根因是"登记与读数不同源"**：运行时有一把尺子 `parse.unclaimed_mechanic_spans()`
（`env._execute` 写 `state.unsupported` 用的就是它），而台账只读 `parse_skill().unparsed`
（里面只装**已登记**的那几种标记）⇒ 174 条两边都空。

## 改法（只补诊断，**不改结算**）

在 `coverage.classify_skill()` 的「读不出效果、又没有未认领片段」那一支里调用**同一个**函数
`parse_mod.unclaimed_mechanic_spans(skill)`，把片段按 `{机制词}：{原句}` 登记进台账：

- **按分句去重**：同一个分句常被多个机制词命中（「若敌方本回合更换精灵」同时命中「若」与「回合」，
  实测被记成两条、把频次刷了两遍）⇒ 按分句文本去重；
- 连**一个已登记机制词**都没命中的 22 条（防御/减伤/应对攻击/交换/迅捷/下一次攻击…，这些词不在
  `_EXTRA_MECHANIC` 表里）⇒ 归到具名的**「未识别机制」**下，原句写进 `why`（人读得懂），
  **不留匿名桶**；
- 档位一个字没动：这 174+22 条**仍然是 PARTIAL**，可模拟实体仍是 **344/824**（这次动的是台账，不是引擎）。

- **配置**：v3 新增 `damage.initiative_condition`（`ENGINE_HYPOTHESIS`，reason 里写明两条假设：
  「敌方攻击」按 `kind=='skill'` 且 `is_attack` 判；加成加在**威力**上）。legacy / v2 不声明。
- **结算**（`env.py`）：`step_joint` 把 `order_actions()` 的执行序列记在 `state._order_index`（只给结算用、**不进观察**）；
  条件 = **我排在敌方那一手之前** 且 **敌方那一手是攻击**。成立 ⇒ `power = int(power × (100+pct)/100)`
  + 事件 `initiative_condition_applied`；不成立 ⇒ 事件 `initiative_condition_skipped`（带原因）。
  自由动作（PVP 魔法）不是联合结算，会把 `_order_index` 清空，避免读到陈旧值。

### 怎么发现的

批次八做完 `扇风` 之后核对它的邻族，随手查 `skill_000763 回收`（「造成魔伤，**若敌方本回合更换精灵**，敌方失去4能量。」）——
台账说 **SIMULATABLE_UNVERIFIED**，可它的条件根本没实现。追下去发现三件事同时成立：

1. 解析器把「敌方失去4能量」读成了一条**无条件**效果（`foe_energy_loss`）；
2. `unclaimed_mechanic_spans()`（**正是** `env._execute` 写 `state.unsupported` 用的那把尺子）
   **明确报出**「若：若敌方本回合更换精灵」—— 也就是说**引擎自己都在回执里说这段没结算**；
3. 而分类器的第一支是 `if parsed.effects and not parsed.unparsed: SIMULATABLE` ——
   它**只看"未认领标记"，不看"未认领片段"** ⇒ 台账说「描述被完整读出且引擎会结算」，
   与引擎的 `unsupported` 直接打架，而且台账那句是**假的**。

### 改法与判据

`coverage.classify_skill()` 的「可模拟」多一个**必要条件**：`unclaimed_mechanic_spans()` 里没有**残余**片段。
「已声明能力覆盖的词」不算残余（连击 / 号位 / 传动 / 先手条件 / 敌方失能）—— 认领口径与 `env.py`、服务端
**同一份读数**（`coverage.declared_capabilities_of()`）。档位只会因此**更保守**，不会更宽松。

判据：`roco/tests/test_effect_coverage.py::UnclaimedSpanBlocksSimulatableTest` **4 条** ——
① 合成「有 effect + 一句未认领机制」的技能 ⇒ 必须 PARTIAL（修前是 SIMULATABLE）；
② 反证：删掉那句 ⇒ 必须回到 SIMULATABLE；③ 已声明能力覆盖的词不算残余（连击的例子）；
④ 台账级不变量：**每一条可模拟都不许有残余片段**（从解析层重算，非循环）+ 这道闸门至少拦下 50 条。
另有 3 条**旧判据改钉**（`KNOWLEDGE_ONLY` → `PARTIAL`，意图不变：声明能力前后档位必须不同）——
「基础伤害照常结算、只有连击那一段没结算」本来就该是 PARTIAL，旧口径把它算成"只有资料"正是同一个洞的另一面。

所以「动态」在这里不是数字好看，而是**合法动作表真的会变**——判据直接量 `legal_actions`。

### 改法（与批次八/九同一套）

  不造"最低 0"的自造下限 —— 负能耗交给既有的 fail closed）；
- 结算：`effective_skill_cost(pet, skill, cfg, *, weather, foe_status_layers)` 新增层数入参，

### 改法

- `schema.py`：`PetState.skill_ramps`（`{skill_id: {power|cost|hits: int}}`），**只在非空时进序列化** ⇒ legacy 指纹不变；
- `parse.py`：`_PER_USE_RAMP` + `Parsed.per_use_ramp` + `resolve_per_use_ramp()`（声明能力才补 Effect、认领「每」那个机制词）；

- `env.py`：`_skill_ramp()` 读累计量、`_accumulate_per_use_ramp()` 在 `step_joint` 的每手之后累加；
  三条结算路径各接一次 —— 能耗（`effective_skill_cost`）、威力（伤害路径）、连击数（出手次数）。

  只翻**挨打那一方配招里真的带着的**技能（没带在身上的技能不该被强化）。
