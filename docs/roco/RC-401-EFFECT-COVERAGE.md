# RC-401 效果覆盖台账 + 第一条按覆盖收益迁移的原语（连击）

> 台账模块：`roco/src/roco_env/coverage.py`（`python3 -m roco_env.coverage`）
> 报告：`reports/roco/rc401/effect-coverage.json`
> 守卫：`roco/tests/test_effect_coverage.py`（5 条）、`roco/tests/test_multi_hit.py`（7 条）

## 为什么先做「尺子」

RC-401 的施工口径是「**按覆盖收益**增量迁移效果原语，不一次重写 68 个」。但在这之前，
仓库里**没有任何地方**回答「现在能跑多少、下一条该实现哪个」：`skills.json` 里 824 条记录的
`effect_support` 一律写着 `unsupported`（导入期的保守标注），而 `traits.py` 只登记了 12 条特性。

所以第一条交付是**覆盖台账**：拿 `parse.parse_skill` 逐条跑 579 条战斗技能，拿 `traits.TRAITS`
的登记状态给 245 条特性定档，并把「解析不出来的原因」按频次排序——那就是下一步的依据。

### 四档（沿用 RC-403 的词汇）

| 档位 | 含义 |
|---|---|
| `FULL_VERIFIED` | 有实现且有一手/实机证据（目前只有 6 条特性走 `traits.py` 的 FULL） |
| `SIMULATABLE_UNVERIFIED` | 描述被完整读出且引擎会结算（**不等于**实机核验过） |
| `PARTIAL` | 读出一部分，仍有没认领的机制片段（引擎**不做部分应用**，如实登记） |
| `KNOWLEDGE_ONLY` | 只有文字资料，引擎不会结算 |
| `REFUSED` | 明确拒绝实现（缺一手证据，理由写在 `traits.py`） |

### 关键口径：覆盖率是「数据 × 已声明能力」的属性

同一份数据，**legacy 口径与候选口径的覆盖率本来就不同**。台账因此把「已声明能力」显式带出来：

| 口径 | 可模拟实体 | 战斗技能可模拟 | 说明 |
|---|---|---|---|
| 未声明连击（legacy / v2） | 473 / 824（57.4%） | 467 | 连击一律算未实现 |
| 声明连击（`mobile_s4_candidate_v3`） | **507 / 824（61.5%）** | **513** | 静态连击被结算，动态连击仍算未实现 |

## 第一条原语：连击（multi-hit）

**为什么是它**：579 条战斗技能里 **67 条** desc 含「连击」，是除「特性未登记」之外频次最高的
未实现机制。而在实现它之前，`effects.py` 的伤害公式虽然**有** `hit_count` 参数，却**永远传 1**
——那 67 条技能被静默地按单次结算（这正是这个仓库最不允许的那种缺陷）。

**做法**（三条纪律）：

1. **静态读得出才结算**：`(\d+)\s*连击` → `Parsed.hit_count`；`1连击` 就是 1，`3连击` 就是 3。
2. **动态绝不猜**：`连击数+1` / `连击数永久+1` / `连击数翻倍` / `变为3连击` 一律进 `unparsed`，
   如实登记为未实现——它们的取值依赖印记层数/应对结果/使用次数，没有一手证据。
   静态基数仍可用（例如「1连击，敌方每有1层星陨印记，连击数+1」按 1 次结算 + 那条加成登记）。
3. **只有配置声明了能力才生效**：`damage.multi_hit`（`mobile_s4_candidate_v3` 声明，
   legacy / v2 **没有这一块**）。没声明 ⇒ 恒定 1 次，且「连击」照旧留在 `unparsed` 里被登记
   ——**legacy 逐位不变就来自这里**（8 条 golden 指纹全绿）。

结算后：伤害事件带 `hits: N`、日志写「（N 连击）」；这两处**只在 `hits > 1` 时**出现，
所以 legacy 的事件与日志一个字节都没动。

## 实测

| 项 | 值 |
|---|---|
| 静态连击技能被结算 | 46 条（67 条含连击 − 21 条另有未认领片段/纯动态） |
| 3 连击伤害 | 19 → **57**（正好 3 倍，确定性） |
| legacy 同技能 | 19（未声明能力，不变） |
| Python 测试 | 371 → **383 条 OK**（新增 5 条台账 + 7 条连击判据） |

## 如实边界

- `SIMULATABLE_UNVERIFIED` 只是「描述被完整读出且引擎会结算」，**不是**实机核验；
  伤害公式本身是社区假设（`effects.py::_community_v1`，非官方）。
- 连击的**逐次结算语义**（每次是否单独触发附带效果、暴击/取整是否逐次）没有证据，
  当前按「单次伤害 × N」处理，属于 `ENGINE_HYPOTHESIS`。
- 台账的收益排序粒度到「原语」，不是到具体句子；特性那 233 条「未被登记」也需要逐条定档。
- 下一步按同一把尺子排序：**选择（20）→ 传动（13）→ 随机（11）**，以及把 233 条未登记特性
  按「实现成本 × 覆盖收益」分批登记。

# 批次二（第 100 轮）：特性层的工作清单 + 两条条件可判的入场特性

## 为什么需要「特性工作清单」

RC-403 的分类显示 **609 只精灵卡在特性那一件上**，而特性有 **245** 条 —— 不能一起上。
所以先按**覆盖收益**排序，再动手：

`python3 -m roco_env.coverage` 现在同时产出 `reports/roco/rc401/trait-worklist.json`：

| 就绪度 | 条数 | 含义 |
|---|---|---|
| `registered` | **14** | 已登记（12 条 A/B/C 组 + 本轮 2 条） |
| `ready` | **2** | 触发钩子已知 **且** 描述能完整读出 —— 可以动手 |
| `effect_unparsed` | **32** | 知道什么时候触发，效果读不出来 |
| `trigger_unknown` | **197** | 效果也许读得出，但**不知道什么时候触发** |

**排序依据是「实现它能让多少只精灵变成全可模拟」**（`pets_blocked`），不是「哪条看起来简单」。
当前唯特性阻塞的精灵：**481 只**（比上一轮的 485 只少了 4 只，正是本轮入库那两条解锁的）。

**触发词只认闭集**：`TRIGGER_HOOKS` 里只放引擎**真的有的**钩子
（`入场时/登场时/换上时/入场后 → on_enter`、`攻击时/使用技能时 → on_action`）。
识别不到就是 `trigger_unknown` —— 效果读得出来 ≠ 知道它什么时候触发，
而**按错时点结算比不结算更糟**（那是静默错算）。

## 入库的两条（`traits.py`）

| 特性 | 精灵 | 条件 | 效果 |
|---|---|---|---|
| 图书守卫者 | 书魔虫 / 书卷守护 / 古卷执政官 | 自己魔力值为 1 | 双攻 +100% |
| 构装契约者 | 古卷匣魔像 | 敌方魔力值为 1 | 双防 +100% |

**为什么这两条可以入库**：触发时点明确（`on_enter`）、效果明确（self_stat）、
而且**条件可判**——「魔力值是否为 1」只有在**声明了魔力**的配置里才判得了。
legacy 里 `mana` 是 `None`（没有这条概念）⇒ 条件不可判 ⇒ **不结算**，行为逐位不变
（8 条 golden 指纹全绿）。

**效果**：`SIMULATABLE_UNVERIFIED` 从 **8 只 → 12 只**（+4：那两条特性挂了 4 只精灵），
`PARTIAL` 614 → **610**。
