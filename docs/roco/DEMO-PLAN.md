## 1.5 P1 的真实失败样例（用户实测，不是假设）

**用户原话**：气泡反复只说「某技能这一手不稳…先看区间再定（最坏尾部…）」，**明确感知为没用**。

### 机制（已定位到代码，不是文案问题）

`src/coach/roco-experience.js` 的 `rocoHintText(plan)` **只拿到 `plan`**，拿不到局面：

```js
export function rocoHintText(plan) { ... }
//   fragile 时：
//   return `「${plan.recommendation}」这一手不稳：对手换个选择就要亏约 ${gap}，先看区间再定${tail}`;
//   tail = `（最坏尾部 ${worst.min} ~ ${worst.max}）`
```

于是**每一手「脆」的局面都落到同一个句式**，只有技能名和数字在变——这正是用户说的
「模板换数字」。而且它**不可行动**：`先看区间再定` 是一句工程话，不是决定。

### 因此 P1 的验收不是「换一句文案」，而是（全部要满足）

| # | 要求 | 怎么验 |
|---|---|---|
| P1-a | 折叠层必须因局面产生**不同的**建议 | 8—12 个差异明显的真实局面，归一化数字后**句子形状**至少 6 种，且单一形状不超过 60% |
| P1-b | 每条建议说清 **做什么 / 为什么是现在 / 一个关键风险** | 三个字段都要非空，且 `做什么` 必须点名动作或明确的「观察/沉默」立场 |
| P1-c | 结合**换宠博弈、速度、能量、状态、后备、上一回合** | 每个局面必须有 ≥2 个这些维度真的参与了判定（在 `evidence` 里可核对） |
| P1-d | **无稳定优势时允许沉默** | 平稳局面必须 `silent`/`defer_to_review`，或给出「再观察」而不是硬答 |
| P1-e | 工程术语**只进展开证据或开发者面板** | 气泡文本里不得出现 `区间/尾部/margin/score/种子/coverage/state_version/{/}` |
| P1-f | 提示**自动出现**，不依赖玩家点「让小芽看一眼」 | 浏览器实测：玩家不点任何按钮也会出现 |
| P1-g | 旧状态下的建议**必须失效** | 换人/推进后旧提示不再挂着（已有守卫，要保持） |

### 实测基线（修复之前，10 个真实局面，`tests/evals/roco/coach-positions.test.js`）

| 句子形状（数字归一化后） | 出现次数 |
|---|---|
| `可以优先考虑「◆」，注意对方可能◆（最坏尾部 # ~ #）` | **6** |
| `可以优先考虑「◆」，注意对方可能换上第#位（最坏尾部 # ~ #）` | **2** |
| `「◆」这一手不稳：对手换个选择就要亏约 #，先看区间再定（最坏尾部 # ~ #）` | 1 |

**10 个互不相同的真实局面（收人头 / 属性克制 / 被抗 / 我方残血有健康后备 / 能量不足 /
对手带异常 / 必须补位 / 均势 / 对手高能量 / 速度先后）产出的句子只有 3 种形状，
其中 8 条是同一种。**「尾部」出现在**每一条**里。

这条测试当前**应当是红的**——它描述的是目标行为。它同时是修复的验收证据：
归一化把引号里的技能名、精灵名和所有数字都替换成 `◆`/`#`，所以「换个技能名和数字」
不会被算成不同形状。

**不声称**：P1 不声称这套建议「更好」——那是真人盲评（W5-05）。P1 只声称
「不再是同一个句式的数字变体，且每条都能指出做什么/为什么/风险」。

## 4. 这一阶段不动的东西（防止为了 Demo 破坏已有纪律）

- **不为 UI 扩大模型协议**：`public_planner_state` 保持最小；UI 用并行视图。
- **不抓官方图**：素材许可不明时用自制色块/剪影/emoji。
- **不据单世界数字声称能力**：一律 1,752 口径 + 配对差异。
- **不打开 `on`**：模型在 Demo 里是「可观测的对照项」，不是决策者。
- **不删旧测试**、不把验收脚本改成只测接线。
- 模型/评测线**暂停但不回滚**：产物与预注册文档原位保留。

### P0-7 的一处**有意偏离计划**

计划里写的是「新建 `scripts/roco/demo-product-acceptance.mjs`：7 条产品判据 + 截图 + 每步 DOM 快照」。
实际做法是**把产品判据继续扩进 `demo-acceptance.mjs`**，而不是另起一个脚本。理由：

- 同一个页面、同一套启动/驱动/截图/CSRF 机制，另起一份就是把它们抄第二遍；
- 两份脚本必然漂移（改一处忘一处），而它们验的是**同一件事**——「这一页是不是产品」。
  「两份验收对同一页给出不同结论」比「只有一份」糟得多。

计划要的三件东西都到位了：**一条命令**、**截图**、**每步 DOM 快照**。

**DOM 快照抓到的第一个问题是我自己的检查器**：第一版它扫 `JSON.stringify(snapshot)`，
于是每一份都命中 `{"`——那是快照自己的 JSON 包装。检查器写错会让它看起来「很严」，
实际量的是自己。收窄成**逐字段扫玩家可见文本**之后，`datasets`（`data-roco-*` 验收钩子）
明确不在扫描范围内，因为把「登记在案的验收钩子」算成泄漏，等于要求验收脚本不能留下证据。
