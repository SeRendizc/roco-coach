# 训练路线图：4B / 27B / learned value 是三件不同的事

**这份文档存在的唯一理由：这三件事在过去的对话里被混着叫过「模型训练」。**
它们的目标、后端、硬件、产物与评测口径**没有一处相同**，混称会直接导致
「4B 训完了所以策略模型也有了」这种结论——而那个结论是错的。

| | 4B v4 | Qwen3.8-27B | learned value / policy prior |
|---|---|---|---|
| **它是什么** | 局内低延迟的**工具路由**适配器 | 同一件事（工具路由）在更大基座上的一次亲训 | 战斗**价值函数 / 动作先验** |
| **输入** | 题面 + 公开局面提示 | 同左 | 局面张量（规则引擎导出的状态） |
| **输出** | 一个工具名 + 参数（或 `stop`） | 同左 | 一个标量（价值）/ 一组动作分数 |
| **后端** | MLX（mlx-lm 0.31.3，`mlx_lm.lora`） | MLX（同左） | PyTorch + CUDA |
| **硬件** | Apple M5 Pro / 48 GiB 统一内存 | 同左 | Windows + RTX 3060 Laptop（**另一台机器**） |
| **产物** | `.models/adapters/qwen35-4b-tool-v4/` | `.models/adapters/qwen38-27b-tool-v1/` | 尚未定义（`checkpoints/` 下现有的是干预模型，不是价值模型） |
| **评测口径** | 288 条单世界门禁 + 逐任务配对 | **同一把尺子**（同任务集、同判定器、同提示摘要） | **口径还没定义**：这个模型的判据是价值校准 / 配对胜负，不是工具选择通过率 |
| **现在到哪了** | **已完成**（工具路由这一环） | **未开始**：权重没下载、没训练、没有任何性能数字 | **未开始**：连口径都没定 |

---

## 1. 4B v4：完成的是**工具路由**，不是战斗策略

**能说的：**
- 它在 `tests/evals/agent-tasks-v1.jsonl` 这套**构造任务集**上，把「该调哪个工具、参数对不对」
  这一环的判据通过率做得比基座高；产物与逐任务配对都在
  `reports/roco/shadow-replay-sft-v4.json`，判据先写在
  `docs/roco/W4-04-SFT-PREREGISTRATION.md` §2。
- 那份预注册里 P1—P8 的逐条结论、以及「哪些数字被重测改掉了」，都在同一份文档 §6。
  **本文不复述具体数字**：数字一旦被搬出它原来的上下文（哪套窗口集、哪个提示、哪把尺子），
  就会变成另一句话。

**不能说的：**
- ❌「4B 训完了，所以战斗策略有了。」它**不输出**出招、不输出换人决策、不评估局面好坏。
  它只决定「接下来调哪个工具」。
- ❌「4B v4 可以上线了。」`ROCO_LOCAL_MODEL` 默认 `off`，页面走的仍然是规则臂。
- ❌「通过率 = 胜率。」这里没有胜负，只有判据过没过。
- ❌「v4 比 v2/v3 全面更好。」总数上升的同时存在**逐任务退化**，预注册 §6.1 的 P7 就是为此设的。

**两个口径必须分清**（这也是 `tests/evals/claim-honesty.test.js` 的机器检查对象）：
- **窄口径**：每任务 1 个世界 → 288 个窗口，用于 arm 之间的横向比较；
- **宽口径**：每任务取满 9 个世界 → 1,752 个窗口，**只有它可以用来描述「模型在这套任务集上的整体能力」**。

拿窄口径当整体能力说，测试会判红。这不是文字洁癖：窄口径是更简单的窗口集，
用它描述整体能力会把退化条数盖住。

## 2. Qwen3.8-27B：**用户亲训**，Mac 上做量化推理与教学式 LoRA

- **目标分工**：27B 在这个项目里是**离线**角色——teacher / 评测 / 数据生成 / 慢速深度复盘，
  **不进**约 3 秒的局内关键路径。`models/registry.json` 的 `not_downloaded` 段写的就是这个定位。
- **谁执行**：**你**。逐步手册在 `docs/roco/QWEN-27B-USER-RUN-GUIDE.md`。
  本仓库只提供**只检查、不执行**的引导脚本（`scripts/train/`，见手册 §8 的自检输出）。
- **训出来的是什么**：**工具路由**。它和 4B v4 是同一件事在不同基座上的一次尝试，
  **不是**战斗策略模型、**不是**价值模型。这一点在台账的 `claims.this_is_not` 里必须写明。
- **现在到哪了**：权重没下载、没训练、没有任何性能数字。
  唯一与 27B 有关的实测是**本机硬件**（48 GiB 统一内存、738.7 GB 可用磁盘、mlx-lm 0.31.3）；
  与 27B 有关的尺寸/内存数字全部是**估算**（手册 §5 与 §10）。
- **一个必须先解决的未知数**：27B 的 LoRA 峰值内存**没有实测来源**。
  从 4B 的实测锚点外推会得到 28.1 GB 与 79.8 GB 两个读数，本机 48 GiB 落在两者之间。
  所以正确流程是**先跑 1—2 个 iteration 的冒烟量峰值，再决定跑不跑完整轮**——
  这就是 `npm run train:prereqs` 在本机给 `must-measure` 而不是 `ready` 的原因。

## 3. learned value / policy prior：留给 **Windows 3060 Laptop**，PyTorch/CUDA

### 它是什么
- **value**：给定一个局面，预测「从这个局面往下走，赢的概率 / 期望收益」。
  它要能在搜索或排序里替代手工评分。
- **policy prior**：给定一个局面与合法动作集合，给出动作的相对优先级。

两者都**不是**聊天模型，也**不是**工具路由。它们的输入是规则引擎导出的局面张量，
输出是数。它们的评测判据（价值校准、配对胜负、与规则基线的对局结果）**目前没有定义**——
所以现在能做的只有「把硬件事实记录下来」这一件事。

### 这一轮**只**做「记录硬件事实」的步骤（**不连接那台机器**）

在那台 Windows 机器上、由你手动执行，把输出抄进台账：

```bat
:: 显卡与驱动
nvidia-smi --query-gpu=name,memory.total,driver_version,compute_cap --format=csv

:: 内存与系统
systeminfo | findstr /C:"Total Physical Memory" /C:"OS Name" /C:"OS Version"

:: Python / CUDA 工具链（装了再看）
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
```

台账放在 `reports/roco/train-value/ledger.json`（**新目录，这一轮不创建**），字段至少要有：

| 字段 | 含义 |
|---|---|
| `gpu.name` / `gpu.vram_gb` / `gpu.compute_cap` / `gpu.driver` | 显存上限与 CUDA 能力，决定 batch / 模型宽度 |
| `host.ram_gb` / `host.os` | 主机内存与系统版本 |
| `toolchain.torch` / `toolchain.cuda` | 版本；`torch.cuda.is_available()` 必须为 `true` 才算能起步 |
| `scope.declared` | **写明**：这台机器只做 value/policy，不参与任何 Mac 侧的推理 |

这些命令**这一轮一条都没有执行**（那台机器不在本次范围内，也没有任何脚本会去连它）。

### 硬边界：**不许**把两台机器的显存拼起来用

- Mac 的 48 GiB **统一内存**与 3060 的**独立显存**是两个互不相通的池子。没有 NVLink，没有 RDMA，
  也不是同一个地址空间。
- 因此**不允许**任何形式的跨机模型并行 / 流水线并行 / 参数分片
  （`torch.distributed` 跨机、`accelerate` 多机、任何「一半在这台一半在那台」的方案）。
- 也不允许把 Mac 的内存当 3060 的「溢出区」——那只会变成一次几百 MB/s 的往返。
- **判据**：任何一步如果它的内存需求超过**单台机器**的上限，那一步就是**出界**，
  应当缩小模型/精度/序列长度，而不是想办法把两台拼起来。

## 4. 两机协作靠什么（只有三种东西可以过边界）

| 过边界的东西 | 形式 | 必备字段 | 不过边界的东西 |
|---|---|---|---|
| **版本化数据** | 文件 + sha256 | 生成脚本、参数、`split_mode`、行数、sha256 | 实时服务、FIFO、端口 |
| **checkpoint / 适配器** | 权重文件 + 配置 | 基座 `repo_id` + `revision`、训练配置、权重 sha256 | 绝对路径、缓存目录、密钥 |
| **评测报告** | JSON | `identity` 块（模型 / 适配器 / `adapter_sha256` / `prompt_digest`）、判据版本、逐任务行 | 结论性文字（报告只放数字与判据，结论写在文档里） |

三条具体规矩：

1. **`identity` 块是硬要求。** 第 37 轮的事故就是报告里没有「这份是谁跑出来的」，
   于是 `-sft-v2.json` 里装的是 v1 的成绩，而没有任何检查会发现。
   现在 `npm run train:verify-artifacts -- --step eval` 会核对
   「文件名 ↔ `identity.adapter_basename` ↔ 权重 sha256」三者一致。
2. **`prompt_digest` 是「同一把尺子」的机器判据。** 两份报告要配对，
   它们的 `prompt_digest` 必须逐字节相同，否则配对差异没有意义（检查器会判红）。
3. **格式差异要显式处理，不要假装无缝。**
   Mac 侧产出的是 **MLX safetensors 适配器**，3060 侧吃的是 **PyTorch state_dict**；
   两者**不能直接互读**，转换需要显式脚本。**本仓库目前没有这样的转换脚本**——
   需要的时候再写，并且要带上一次前向输出对齐的自检（转换后同输入必须同输出）。

## 5. 边界与红线（写给以后接手的人）

1. **不要混称。** 说「模型训练完成」时必须写清是哪一条：工具路由 / 价值 / 策略。
   本仓库里 `reports/roco/shadow-replay-sft-v4.json` 代表**工具路由**，不代表后面两条。
2. **不要顺手扩大。** 27B 是离线 teacher 角色，不进局内关键路径；3060 只做 value/policy。
3. **不要在文档里写没有产物的数字。** 任何通过率/延迟/内存都必须能指到一份带 `identity` 的产物。
   没有产物的数字，按本仓库的做法要么重测，要么撤回。
4. **不要为了填表格编校准数字。** 工具选择这一项**校准不适用**（输出是离散工具名，判定器给 0/1），
   这一点 `docs/roco/W4-04-SFT-PREREGISTRATION.md` §3 已经写死；
   需要校准的是输出概率并用阈值做决策的那一类模型。
5. **不要把两台机器的内存当一块用。** 见 §3 的硬边界。
6. **不要动 4B v4 的产物。** 它是目前唯一有完整产物支持的工具路由适配器；
   覆盖掉它，回滚就没有锚点了。`scripts/train/` 里有守卫会对受保护路径直接抛错。
