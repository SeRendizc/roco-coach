## 2. 方案与拍板（Lead 已定）

- **A（采用）**：保留 100 上限 + Map 插入序当 LRU（命中就 `delete+set` 挪队尾）+ 建会话前先回收。
- **B（不做）**：加 purge 端点 —— 它把"重启"换成"手动清"，**不解决"卡死全队"**，还多一条 API 面。
- **C（不做）**：只降 TTL / 只提上限 —— 降 TTL 会**踢真人**；提上限只是**把撞墙推后**，100 与 500 同样没有依据。

## 3. 改了什么（`src/server/index.js` 会话层，+53/−4）

1. 常量集中：`SESSION_CAP=100`、`SESSION_TTL_MS=8*3600000`（数值不变，注释写清依据与出处）；
2. `sessionIdOf(req)`：Cookie 解析**只有这一处**（原来 bootstrap 与 POST 各写了一遍同一段正则）；
3. `touchSession(id,s)`：命中就挪到 Map 队尾 ⇒ **队头 = 最久没用过**；两处调用
   （bootstrap 命中、POST 过了 CSRF 校验之后 —— 后者正是"正在用的页面不该被当成最旧的淘汰掉"）；
4. `reclaimSessions(now,need)`：① 清过期 ② 仍然不够就从队头淘汰（返回淘汰条数，供判据/排障读）；
5. bootstrap 未命中时：**先回收再建**；原来那句 `if(sessions.size>=100) throw fail(429,'本机会话过多，请重启服务')`
   换成**不变量守卫** `throw fail(500,'会话表回收后仍然没有空位…这是内部不变量被破坏，不是本机会话过多')`
   —— 按上面的实现它**到不了**；留着是因为"上限不许删"，而它的语义与实现一致（不是一句走不到的假话）。

> ⚠ **文案偏离说明**：Lead 说"429 文案要改，要么是'真满了且淘汰也救不了'，要么就不该走到这里"。
> 我选**后者**：方案 A 下 429 的语义已经不存在了，所以不再保留一个假的 429，
> 换成一个"只在回收逻辑被改坏时才会触发"的 500 不变量。**上限没有被删**，只是不再等于死路。

## 5. 对探针的影响 + 持久 profile 的结论

- **修好之后**：`browser-live-acceptance` / `browser-workshop-acceptance` / 我那三个脚本**不会**再因为
  会话满而 429。但如果哪天会话被淘汰/失效，拿到的是 **403「会话已失效，请刷新页面」**（POST 路径），
  **不是**"没发请求" ⇒ 探针要把这两件事分开判（今天那条误判链正是把 429 当成了"产品没发请求"）。
- **结论：探针默认复用 `tmp/browser-profile/`（Lead 已定）**，一轮省 ~16 格。
  ⚠ **必须同时遵守的 caveat**（本轮最有价值的发现之一）：持久 profile 会**带着上一轮的 localStorage**
  （`roco.box.individuals.v1` / `roco.workshop.loadouts.v1` / `roco.workshop.teamconfig.v1`）
  ⇒ **判据的初始状态不再干净**，"省会话"会换成"读数不可信"。
  **定案：profile 持久、localStorage 每轮清**（开跑前一个 `Runtime.evaluate('localStorage.clear()')`）。
  > `tmp/BROWSER-LOCK.md` **不在本任务写域**，这四行请 Lead 挪进去（或授权我再动）。
