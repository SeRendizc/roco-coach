# Roco Coach 长线计划与每两小时监工规则

生效：2026-09-29。负责人：DSH 负责实现；当前 Codex 体检聊天负责检查稳定性、用户可感知效果与方向。用户新增优先级：立绘、全部已拥有精灵的训练场战斗尽快完成。模型分工的进一步结论先在聊天说明，用户确认后另写进报告；本文不替用户提前确认。

## 产品目标与判断标准

做一个可以接到不同游戏界面、了解玩家当前处境、给出有根据的建议、记住明确偏好，并帮助玩家逐渐进步的洛手 AI coach。面试展示应由实际运行和可复验结果支撑。

每项功能同时满足：玩家能用；数据与显示一致；失败有相关且诚实的解释；修改可以核验；不会破坏已有闭环。测试数量、资料数量、模型大小不能代替这些条件。

长期主线：精灵培养与比较 → 保留偏好与锁定条件 → 完整六只/每只四技能 → 阵容诊断和最小替换 → 本地六只 PVP 训练 → 有用且克制的局内提醒 → 一件事的复盘 → 下一次不同局面验证理解 → 可独立接入的宿主示例。

## 第一个阶段：近期双优先级，目标窗口为首个 48 小时

这个时间是排期目标，不是已经确认的完成承诺。先核对数据和改动量，遇到缺口要给出具体清单和新的估计。近期同时推进视觉与可玩基础，不等整个 AI 系统完成后才接形象。

### A. 立绘接入

- 按已拥有实例对应的物种和形态建立准确映射。先核对当前数据、形象目录和缺图清单，不写死“已全部覆盖”。
- 列表、详情、候选池、六只队伍、对战使用同一套映射。基础形象先齐，再做技能特效。
- 原始素材保留；生成轻量预览，按需加载、缓存；不在首屏加载整个素材库。缺资源显示明确占位，不偷偷借另一只图。
- 动作、受击、倒下、切换、重新开局保持基础形象，不再因为不存在的变体图片丢图。
- 验收：对所有已拥有实例自动检查路径与解码；逐页核对映射；桌面和手机实测；抽检不同形态、双属性、大图、无图情况，保存截图及加载体积。

### B. 全部已拥有精灵能进行本地训练战斗

- 定义范围为当前已拥有实例清单，而非只允许旧 48 只；对账物种、形态、实例、合法学习表和当前四技能。
- 所有已拥有精灵能够选择、编入符合规则的六只队伍、进入战斗、执行支持的技能或换人、完成结算。不用预置的少数成功队伍替代全量验收。
- 逐只补齐基础行动需要的实现；特殊机制建立明确缺口。未实现的决定性效果不能伪装结算，更不能把“可开局”写成“实机机制全验证”。将可玩覆盖和机制核验分别统计。
- 培养配置需要随战斗入口完整传递。某技能不能运行时显示准确原因和合法可运行的替代方案；这只仍无法构成基本合法配招时，作为未完成项处理，而不是通过改标签算完成。
- 验收：全量逐只完成最小战斗冒烟；覆盖技能使用、换入、受击、倒下、结束；组合测试至少包含不同系别/形态与特殊技能。记录总数、成功数、精确失败 ID、失败步骤和机制缺口。随机六只与玩家实际六只均跑通。

### 同时不可拖延的信任修复

小芽联网与离线使用可用的资料服务；禁止旧游戏内容串入；培养文字、面板、队伍、战斗和小芽读取同一份当前配置；纠正未核验标签和假设环境频率。实现方案参见《给DSH的修复方案》P0-01～P0-05。若这些问题影响新增精灵战斗，则优先打通相关部分。

阶段完成标准：真实页面可看到立绘和全部已拥有范围的选择/对战；全量清单与失败原因透明；至少一条培养→配队→战斗的信息一致；已有功能不出现白屏、失效入口、丢图回归。不得用“数量变多了”宣布完成。

## 第二阶段：第一周，完成真正能用的培养与配队教练

以迪莫为核心先做好一个完整任务，逐步覆盖其它精灵和玩家偏好。

- 当前详情页能识别精灵和最新配置，回答“为什么选这个性格、这四技能怎么搭、培养先做什么”。没有证据的最强结论不编。
- 生成六只、每只四个合法技能；保留锁定精灵；允许在已拥有与全资料范围切换；给主要收益与代价。
- 比较建议、应用、撤销、重新读取一致；数据缺口具体可见。任务不完整时不显示成功。
- 评估首屏只给最重要的 1～3 件修改，不用大段指标压住行动；假设对手与真实统计分开。
- 小芽与详情/队伍 UI 同步改：可读宽度、回答层次、焦点提示、四技能不重复、搜索筛选、正确等级、加载与失败状态。

阶段完成标准：体检中的失败问句逐项重测；浏览器执行完整 6×4 任务；没有旧内容；所有建议可核验、可应用和撤销。增加真实浏览器验收，而不是只补同实现的单元断言。

## 第三阶段：第 2～3 周，教练帮助玩家进步并证明能接入

- 主动提示只在有明确价值时出现；能指出事实、风险、一个可考虑行动；拿不到关键事实时不装懂。静默偏好、重复事件、过期答案与取消均有效。
- 复盘选一个关键决定，说明当时可见信息与合法替代；投降与正常打完分开处理，不写绝对换人口诀。
- 下一次出不同但相关的练习，验证玩家能否解释并选择。陪练记住明确偏好，与未确认猜测分开。
- 实现独立简单宿主，接入当前场景、状态事件和建议显示；挂载、退出清理、缺能力降级都测试。训练场复用同一接口。
- 真实游戏接入单独核对可用且获授权的接口；在此之前只宣称独立宿主与训练场接入完成。

阶段完成标准：不开聊天也能帮助一局；复盘和下一局练习确实连起来；独立宿主可运行；至少做一组有记录的真人试用，记录错误、烦扰、理解变化，而不是模型自评。

## 第四阶段：第 4～6 周，稳定、扩展与面试证据

- 按玩家使用频率与影响逐项补关键机制，使用版本化来源和真实核验用例，避免一次性重写全部引擎。
- 分别统计资料、合法配招、可玩基础、机制实现、实机校准范围，扩展到更多实例与形态。
- 统计请求真实耗时、失败与回退、内存与费用。首屏立即反馈，复杂任务有可取消进度；不把短模型调用当整条体验耗时。
- 根据用户确认的模型方案做公平对比：相同问题、上下文与工具、未见过的测试题、正确调用和完成任务；证明收益后再决定训练或扩大模型。
- 准备五分钟演示、独立宿主示例、失败到修复的证据链、真实能力和限制说明。面试说法不超出结果。

每周末重新安排下一周：先看本周哪些玩家任务真的变好，再决定增加范围。阶段可重叠，验收条件不能省略。

## 每两小时如何监工

已有 `roco-coach` 周期任务更新为每两小时，绑定当前体检聊天；旧暂停任务继续保持暂停。设备和 Codex 必须能够运行；这是定时抽查，不是持续在线告警，也不保证睡眠/关机期间执行。

每次最多做一轮有边界的检查：

1. 读取当前 HEAD、工作区、DSH 当前任务与新增产物；先识别谁正在修改什么，避免两边抢写。
2. 检查服务端口和实际请求、首页及关键入口；页面存在不等于业务正常。
3. 轮换抽查关键功能：资料/上下文、培养一致性、配队完整性、全部已拥有范围/图片、战斗/复盘/教学、宿主接入。每次选择与新改动相关的项，不每轮跑全量长测试。
4. 核对宣称完成项的代码、结果、截图与版本一致；区分旧失败、无法运行的测试、真实回归。
5. 写简短巡检记录：时间、HEAD、服务、可见变化、问题、证据、下一项。发生重大变化才更新用户报告。

巡检记录目录：`docs/roco/review-2026-09-28/codex-healthcheck/巡检记录/`。每次一份小文件，避免反复重写长报告。文件写入如受权限阻挡，先保留当前工作区的记录并报告，不伪称已写入。

## 纠偏与通知

发现白屏、关键按钮失效、主线断链、精灵配置错位、错误数据承诺、开发偏离验收目标时，给已明确识别的 DSH 当前任务一个简短要求：当前版本、具体复现、期望结果、验收截图。不覆盖草稿、不猜目的地、不重复正在做的修改。

同一阻塞连续两轮未变化时，不反复下令和重跑重活；记录阻塞，查依赖，再推进可独立交付的事项。空闲不等于故障，不能仅因没输出就盲目启动工作。

正常且无变化时安静；只在实质进展/阶段完成、故障、方向偏移或需要你处理时通知。通知说清楚玩家能做什么、什么坏了、证据在哪、下一步，不报无意义测试数量，不编剩余时间。

默认监工不修改产品代码、不重启正在使用的服务、不清空数据、不改黄金答案、不下载/训练模型、不租机器、不发布。已有明确授权的工作可以传达给 DSH；新授权边界由用户决定。稳定性修复不能拿“改测试使之变绿”代替。

## DSH 交付格式

每个小阶段提交：问题与玩家行为的前后变化；代码与当前版本；有独立判定依据的正向/反向测试；实际浏览器截图；已知未完成项；下一项。进行中的工作保留断点，报告里区分计划、实现和实测。

参考：同目录两份 2026-09-28 深度体检报告。本计划覆盖旧监工提示中“每项强制模型/RAG/RL”“旧3v3主线”“一律刷全量门禁”等不适合当前目标的要求。
