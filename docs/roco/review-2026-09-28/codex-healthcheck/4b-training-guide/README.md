# 你接手 4B 的详细指导

日期：2026-09-29。对象：Roco Coach 当前本地 Qwen3.5-4B-4bit 与 v8 适配器。27B 暂缓。本文是训练方案，不代表新模型已训练、已接入或已通过验收。

## 1. 我的判断：值得训练，但先把训练目标缩小

**4B 最适合做本地小芽的“理解问题、找对资料、选择下一步工具”能力。其次是根据已经查到的结果，给出短而具体的解释。**

它的价值是：普通问题可以本地处理；云端暂时不可用时仍有一部分可用能力；小芽能根据当前页面、精灵、队伍和上一回合主动提出建议；面试时，你能拿一条完整执行记录解释“问题如何变成工具调用，结果如何变成建议，以及失败如何处理”。

4B 可以辅助组织复杂配队任务，但合法性、队伍完整性和战斗规则应由程序校验。完整六只队伍、每只四个技能，可以分步检索和检查，不能要求模型凭记忆一次吐出全部正确答案。

**不要先训练它背几百只精灵的数据库，不要先做强化学习，不要把解决立绘、数据错位、战斗引擎缺机制寄托给微调。** 这些问题需要代码与数据修复。模型不知道页面实际上选中了谁，训练再多也会答错对象。

建议顺序：第一版先把选工具做好；第二版补有依据的短解释；第三版再做多步配队、局末复盘。27B 在这条链路跑通之前没有必要继续占用精力。

## 2. 现在有什么，哪些证据还不够

这次检查确认本地 4B 权重、v8 适配器和 MLX 环境都存在。产品的本地模型默认关闭，当前服务有云端连接；“文件在磁盘上”和“小芽实际用了 4B”是两回事。

当前旧数据：

| 项目 | 已核实的情况 | 意味着什么 |
|---|---|---|
| 训练/验证/测试数量 | 2403 / 362 / 107 | 数量不算没有基础，但不能只看条数 |
| 已删除的工具 | `inspect_training` 在三份数据中分别有 128 / 8 / 8 条目标答案，当前工具注册表没有它 | 直接续训会继续教模型使用不存在的接口 |
| 新工具测试 | 测试集中没有 `query_rules`、`evaluate_team`、`compare_team_change` 的调用正例 | 旧测试不能证明这些能力练好了 |
| 输入格式 | 有的样本没有工具清单、没有之前的工具结果；有的包含它们 | 模型可能学会按题型猜答案，而非根据已有结果决定下一步 |
| 实际产品接口 | 当前服务给本地规划器的工具只有 7 个；完整注册表有 12 个，旧训练覆盖了另一组 | 学会一个工具也不等于产品会允许它调用 |
| 旧测试成绩 | v8 工具覆盖记录 17/20；判分主要看工具名 | 选对名字，不代表参数对、拿到了正确精灵资料或最终建议能用 |

结构检查得到 144 条不存在工具的目标答案。其余样本通过参数形状检查，也**不等于参数语义正确**。检查器给部分工具补了宿主负责的 `state_version`，只为检查结构；这个字段不应要求模型生成。

旧训练日志中，900 步约 33 分钟、峰值内存约 16.1GB。这是当时的短样本和配置记录，不能据此承诺新训练的耗时。旧样本最长约 411 token，原 768 上限没有截断；下一版加入真实上下文和工具结果后，应重新测长度。

另外，训练与推理对 Qwen 的思考模板处理有差异：推理显式关闭思考，训练默认模板没有显式传同样的开关。现在还不能据此断定已有模型失败的原因，但正式训练前必须核对实际 token 前缀与答案的训练区间。

## 3. 你和 DSH 怎样分工

**你负责：选择训练目标，审查代表样本，运行训练，比较模型，在真实小芽里判断是否好用。**

**DSH 先交付以下五项，再进入正式训练：**

1. **统一实际接口。** 给训练生成器、测试器和产品共用同一份工具定义、系统提示词、输入组织方式。明确下一版小芽开放哪些工具，不要训练全 12 个却上线只给 7 个。
2. **修正数据。** 清理旧 `inspect_training` 答案；根据现在的培养界面重新标注应查什么、读什么。修复当前精灵、当前队伍和技能的传递，资料通路必须真实可调用。
3. **生成可追溯样本。** 保存问题、页面、真实精灵/队伍上下文、可用工具、之前查到的结果，以及正确下一步。给每条样本标来源、场景组和审核状态。
4. **建立真正的任务测试。** 不只判断工具名，要执行工具，检查参数、结果、停止时机、最终回答和失败回退。测试集在调模型之前冻结。
5. **给你一份接入说明。** 新适配器怎样在独立测试服务中选用；怎样看到实际调用、耗时和回退原因；怎样切回 v8。不要为了训练重启正在使用的主服务。

这些工作与“全已拥有精灵立绘接入、能选入队伍并完成本地战斗”可以同时推进。训练前缺的是可信接口和可信样本，不是再等一批模型文件。

## 4. 第一版具体学什么

第一版只学习当前规划器支持的两类输出：

```json
{"tool":"query_rules","args":{"kind":"pet","name":"迪莫"}}
```

```json
{"stop":true}
```

上面的查询仅在下一版实际工具清单开放 `query_rules` 时适用。`stop` 表示这一轮不再调用工具，后续宿主继续整理结果或回退；不是让小芽默默不回答。

不要自行加 `clarify`、`handoff`、`write_memory` 等新输出，当前程序未必能处理。缺少信息时，由程序把已支持的澄清或失败流程呈现给用户。

建议建立以下场景，比例只是起点，最后按实际使用和错误分布调整：

| 场景 | 训练重点 | 示例验收 |
|---|---|---|
| 查精灵、技能、可学招式 | 对象、查询类型正确；没有 ID 时用接口支持的名字查询 | 问迪莫不能查成当前另一只精灵 |
| 读取当前状态、上一回合、战斗记录 | 当前页面和用户问题确实需要哪个数据 | 未读过当前状态不能假装已经知道血量 |
| 比较行动、模拟分支 | 只使用宿主提供的合法行动；按需调用 | 不能编造技能编号或对手动作 |
| 队伍评估、替换成员 | 使用真实六只队伍与配招，调用实际开放的接口 | 能发现缺员、非法配招和特定弱点 |
| 已有足够结果 | 停止重复查询 | 资料已经完整时不再发同一个工具调用 |
| 缺资料、歧义、过期、工具失败 | 根据现有能力选择补充读取或交给宿主处理 | 不把“没查到”变成自信编造 |

建议初版 1200–2000 条**经过审核的训练决策**，验证和测试各 150–250 条。先手工做 50–100 条代表样本，打通执行与判分，再扩大。不要直接生成几千条相似句子。

停止样本可从约 20%–30% 开始，但不要把比例当目标：更重要的是分清“材料够了”“没必要用工具”和“缺信息但当前无工具可补”。后三者若都只输出 stop，宿主必须通过结果状态决定用户会看到什么。

### 最值得加的成对样本

同一句问题，换上下文，正确答案必须可能变化：

- “给它配招”：当前选中迪莫 / 另一只精灵；目标不同，查询对象不同。
- “下一步怎么打”：当前状态还没读取 / 已读并有合法行动列表；下一步不同。
- “这个技能能学吗”：已有完整可学招式结果 / 只有技能介绍；前者能判断，后者需要继续查询。
- “优化我的队伍”：有完整六只与四技能 / 缺两只成员；不能假装完成相同任务。
- “再查一下”：上一次查询失败 / 上一次成功而用户没有新问题；不能机械重复同一动作。

样本的正确性必须来自当前数据、规则和真实工具结果。可让强模型起草，但强模型也是草稿生成器；它说得流畅不能作为规则正确的证据。

## 5. 数据怎么组织，怎样防止考题泄露

三个文件分别为 `train.jsonl`、`valid.jsonl`、`test.jsonl`，每行是一条 JSON。沿用 MLX 的 `messages` 格式，最后一条 assistant 是标准答案。`meta` 为审核附加信息，不放进模型输入。

示意结构如下，**不能把这个教程样例当作正式数据**：

```json
{"messages":[{"role":"system","content":"这里必须是实际产品共用的完整提示词"},{"role":"user","content":"这里必须是实际产品序列化后的输入"},{"role":"assistant","content":"{\"stop\":true}"}],"meta":{"group_id":"case-family-001","reviewed":false,"source":"真实工具记录路径和版本","contract_version":"待冻结的接口版本"}}
```

按“同一原始战斗、同一队伍、同一问题模板的衍生组”分组，然后把整组划给某一个集合。不要先改写十遍再随机分成训练和测试。建议测试至少保留没在训练出现过的精灵组合、回合记录和问法；不能只换名字。

测试集还需要覆盖所有实际训练的工具，以及不该调用它们的反例。训练中的罕见工具可以少，但不能测试为零。另保留一份完全不参与训练的人工体验题。

附带 `audit_dataset.mjs` 会检查：非法 JSON、未知工具、参数结构、模型乱写版本号、完全相同的输入、组别跨集合、缺少审核信息、测试缺工具正例。它**不能证明**样本符合洛克规则，也不能识别所有同义改写、错误 ID、战斗模拟偏差。

## 6. 从哪里开始训练：推荐重新训练一个 v9

这里的“重新训练”是从现有 4bit 基础模型训练一份新的小适配器，基础权重仍然冻结，不是从零训练一个大模型。LoRA 只训练少量附加参数；MLX 支持在量化基础模型上这样训练。[MLX 官方说明](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)

**推荐新建 v9，保留 v8 做对照。** 原因是旧数据有失效工具、接口范围不同、测试不足。先保留相同 rank、层数等参数，让这轮实验主要回答“数据和接口修正有没有用”。

如果你坚持从 v8 接着训，包里也有 `continue` 模式：较小学习率 5e-6，先试 200 步，并加入约 25% 已重新审核的旧能力样本，防止新能力覆盖旧能力。不要原样回放有错误的旧数据。

注意 MLX 的 `--resume-adapter-file` 在当前安装版本中加载适配器权重，优化器重新创建；它不是连同旧训练状态完整恢复。v8 的 rank=8、scale=20、8 层等结构需要匹配。续训也必须通过同一份新测试。

## 7. 建议参数与实际操作

包内 `lora-v9.yaml` 初始设置：4bit 基础模型、8 层 LoRA、rank 8、scale 20、batch 1、学习率 1e-5、长度上限 1024、只计算答案部分的训练损失。使用机器现有 `.venv-mlx`，不要求安装云端训练环境。

1024 不是固定最优值：先测新样本长度。若真实输入超长，先精简无关材料，确保答案不被截掉；确有必要再加上限。不要为了省内存盲目降到 512。如果内存压力大，可试 `grad_checkpoint: true`，代价是速度变慢；先减少重型并行工作，再讨论加 batch 或 LoRA 层数。

### 第一步：准备真实数据和接口审核

数据默认放在本目录 `data/router-v9/`。也可以用 `ROCO_TRAIN_DATA` 指定其他绝对路径。

```bash
cd /Users/serendizc/Codex/Internship/4b-training-2026-09-29
node audit_dataset.mjs /绝对路径/你的数据目录 --new-data
PYTHONDONTWRITEBYTECODE=1 /Users/serendizc/Developer/roco-coach/.venv-mlx/bin/python token_audit.py /绝对路径/你的数据目录 --max-seq-length 1024
node readiness.mjs snapshot /绝对路径/你的数据目录
```

最后一个命令产生 `READY.example.json`，记录三份数据和关键源码指纹，所有完成标记初始为 false。完成五项检查并写入相应 `evidence` 路径/说明后，另存 `READY.json`：

- `runtime_contract_checked`：产品实际可用工具、生成器和测试器一致。
- `training_serving_prompt_aligned`：训练与推理提示词、序列化、思考开关及 token 前缀/答案训练区间一致。
- `data_reviewed`：代表样本和所有标准答案有可靠来源，旧工具问题已修正。
- `test_frozen`：组别隔离并冻结测试；覆盖实际训练工具。
- `task_evaluator_ready`：已有可重复执行的任务判分，包含参数、工具结果和错误回退。

这不是填表许可。没做的保持 false，先让 DSH 完成对应工作。训练脚本会检查这些标记、证据和文件指纹；数据或关键源码变了，旧 READY 就失效。该检查依赖填写的证据真实，无法自动替你判断证据质量。

### 第二步：20 步试跑

```bash
ROCO_TRAIN_DATA=/绝对路径/你的数据目录 bash train_v9.sh smoke
```

看四件事：是否正常出检查点；内存是否可接受；训练样本有没有截断；抽查模型是否仍能给出完整、可解析的 JSON。20 步只检查训练通路，不能证明模型已经好用。不要把 smoke 模型接到主服务。

### 第三步：第一轮新适配器实验

```bash
ROCO_TRAIN_DATA=/绝对路径/你的数据目录 bash train_v9.sh fresh
```

默认 400 步，每 100 步验证和保存。这是快速比较实验，不是宣布“训练结束”。batch=1、累计=1 时，1200 条训练数据走完一遍通常需要约 1200 步；400 步只接触其中一部分。根据验证结果决定是否开更长的新实验：

```bash
ROCO_TRAIN_DATA=/绝对路径/你的数据目录 ROCO_TRAIN_STEPS=1200 bash train_v9.sh fresh
```

每次 fresh 都是新的适配器实验。不要把它误以为在上一轮 400 步之后继续加 1200 步。先比较 100/200/400 检查点；若验证已恶化，先查错例和数据，不要机械加到 900 或几千步。

可选的 v8 接续对照：

```bash
ROCO_TRAIN_DATA=/绝对路径/你的数据目录 bash train_v9.sh continue
```

每轮输出写入新的 `runs/时间-模式/`，保存配置、审核标记、日志和适配器；不会覆盖原 v8。**本次没有运行任何训练，也没有提供已审核的正式 v9 数据。**

## 8. 怎样判断它真的更有用

至少比较三组：基础 4B、现有 v8、新 v9。使用同一份输入、同一份工具清单、同一份测试、相同生成参数。禁止通过给某一个模型更多提示或更多上下文来制造提升。

| 项目 | 要看什么 | 建议初版准入线 |
|---|---|---|
| 格式与工具 | JSON 可解析、工具存在、参数合法 | 至少 95%，未知工具应为 0 |
| 实际任务 | 对象正确、真实工具结果正确、完成用户问题 | 明确可完成任务至少 90%；不能用格式正确替代 |
| 严重错误 | 编造规则/技能、错精灵、非法配招、无限重复工具 | 固定重点测试中为 0；发现就修样本/程序 |
| 停止与回退 | 足够材料时不多查；缺材料不假装会 | 分类别统计，不能藏在总分里 |
| 体验 | 小芽是否给了下一步能做的建议 | 人工体验题至少 20 个，逐条留输入、结果和判断 |
| 速度 | 从提问到看到有用结果，含冷启动、排队、工具执行 | 记录首次与连续使用的中位数、较慢的 5%；按页面反馈评估 |

这些是建议标准，不是已达到的成绩，也不是未来所有问题都可靠的保证。小样本里一两条就会明显改变百分比；必须同时保留题数和错误列表。

当前规划器的超时计时不包含全部启动和排队，不能只引用模型生成耗时来声称“小芽 1.2 秒响应”。先改善预热、忙碌反馈和整体时间预算。训练与推理同时占用机器时的延迟，不能直接拿来判模型架构优劣。

旧工具覆盖脚本和旧本地质量脚本仍可作为辅助回归，但它们目前不够担当新模型的最终验收。DSH 没有交付真实任务评估前，不要靠低 loss 或“17/20”就上线。

## 9. 第二版再教它说人话

在路由能用之后，再做 500–1000 条“工具结果 → 短解释”样本和单独测试。训练输入必须使用产品真实的 `localPrompt(packet)` 与 `LOCAL_SYSTEM_PROMPT`；若要调整它们，训练、推理和评估一起更新。

当前回答格式是：

```json
{"answer":"两到四句中文，先给结论，再解释依据和下一步。","basis":["已提供材料中的依据"]}
```

当前程序对长度和语言形式有约束，例如 answer 最长 160 字、basis 最多四项。样本要符合当前解析器；解析成功仍不能证明事实有依据。让模型引用输入中实际存在的材料，不能自己编一个依据名字。

最重要的回答训练：能回答就具体回答；材料不够就明确缺哪项；机制未实现就不把模拟结果当实机结论；比较行动时解释当前血量、属性、回合中的关键差别；培养建议给可执行的下一步，不能只说“综合考虑”。

先单独验证这项能力。之后才考虑同一适配器在两种明确系统提示下同时支持选工具和短解释，避免刚加入解释训练就把 JSON 工具调用破坏。

| 第 5 天 | 选验证集表现好的检查点 | 在独立测试服务接入，显示调用与回退身份 | 小芽真实页面和执行记录 |
| 第 6–7 天 | 连续使用，记录不懂、慢、错对象的题 | 修产品问题，整理下一轮错例 | 20 个体验案例和去留结论 |

后续每周一次小规模改进：收集失败 → 判断是数据/代码/模型问题 → 只修对应原因 → 用验证集选检查点 → 最后做一次冻结测试。不要每两小时重训，也不要反复用最终测试选参数；测试被多次用于调参后，补一份未接触的新测试。

我每两小时监工的重点改为：27B 保持暂缓；DSH 是否按真实可用小芽推进；你的训练是否具备可信前置；全已拥有精灵立绘与战斗是否按计划补齐；主服务是否稳定。监工不会自动替你训练或下载模型。
