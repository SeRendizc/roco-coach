# 说人话（小芽面向玩家的文案规范）

> 起因：2026-09-26 产品负责人对着「阵容评估」面板说「**这个说的是人话吗？？整个可读性极差**」，
> 并明确「**这是个系统工程，不只是那个按钮；全部小芽都应该说人话，不应该自娱自乐**」。
> 这份文档是那一轮定下的规范 + 执行办法。**不是建议，是判据要查的东西。**

## 一、八条规则（对**玩家能读到的一切文字**）

| # | 规则 | 反例（真出现过的） |
|---|---|---|
| 1 | **不用内部术语**：口径 / 结构分 / 分母 / 声明假设 / 相对表现 / 契约 / 回执 / 守卫 / 判据 / 台账 / 白名单 / 归一化 / 兜底 / 降级 / 占位 / 证据包 / 提示词 / provider / fallback / token | 「另外四个的**分母**是**声明假设**…相对表现是 **RC-302 的结构分**（ENGINE_HYPOTHESIS）」 |
| 2 | **不对着仓库/代码说话**：本仓库 / 代码里 / 引擎没给 / 我们算的 / 证据包里 / 判据要求 | 「**本仓库**没有这一项的取值」「**引擎没给**这一项」 |
| 3 | **主文案不出现机器标识**：`pet_000118` / `skill_000246` / `own-0001` / `wing_king_force` / `ENGINE_HYPOTHESIS` / `type_row` | 「撞上「**wing_king_force**」这类最吃亏」 |
| 4 | **不出现裸数字**：没有单位/换算的小数（`0.142857`）；**胜率、概率、百分数一律不许**（红线） | 「环境占比 **0.142857**」 |
| 5 | **不出现对象泄漏**：`[object Object]` / `undefined` / `null` / `NaN` | 「例如「**[object Object]、[object Object]**」」 |
| 6 | **加粗只在会渲染的界面上用**：不渲染 markdown 的界面（`textContent` 那一类）里出现 `**…**` 就是错的 | 面板与对话里原样显示的 `**声明假设**` |
| 7 | **先说结论**，单句尽量 ≤ 40 字；整条回答 ≤ 180 字；依据放后面或折叠区 | 开场先讲三段"我们怎么算的" |
| 8 | **把玩家当玩家**：不审计他（「你不许」「必须」）、不解释系统怎么工作、不空转（只回「我在。」「这次没有拿到回答」） | 「这一页不输出胜率、概率或任何伪精确百分数」 |

**允许的例外（写清理由，别扩大）**：
- **HTTP 400 的报错文案**（玩家构造不出来的请求形状）可以带字段名与内部 id —— 它们是给调用方/开发者看的。判据只扫**回答正文与界面文案**。
- **折叠区里的"原始数值与说明"**可以保留内部 id 与裸小数；**主行必须是规则 1–7 的人话**。
- **说"不给胜率"这件事本身**可以说，但要用玩家的话：「这是按阵容结构排的，不代表真实对局里谁赢」——
  不要写「不输出胜率、概率或任何伪精确百分数」。

## 二、怎么执行（三层，缺一层就会反弹）

1. **渲染层**：需要加粗/行内码/换行的界面走 `markdown()`（先转义再替换）。
   已经接上的：`src/client/xiaoya.js`（小芽弹窗/小芽页）、`src/client/team-workshop.js`（面板里的回答框）、
   `src/client/roco.js`（营地页 `#say-reply`）。**新界面默认走它**，不要再 `textContent = 回答`。
2. **判据层**：`tests/roco-plain-speak.test.js` —— 静态扫描"玩家可见文案"（剥注释、只取中文字面量），
   对规则 1–6 计数；**计数只许降不许升**（棘轮：每个文件的允许条数写死在判据里，改小是成绩，改大要写理由）。
3. **复查层**：产品负责人点出来的每一句话，都要在**同一轮**里：① 找到生成它的地方（文件:行号）；
   ② 在真机上复现一次（截图或回执）；③ 改完再复现一次。**只改一个按钮不算完成任务**（他说的"系统工程"就是这个意思）。
