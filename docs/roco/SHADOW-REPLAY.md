# 同 Agent 回放门禁（W4-05 / W5-02）

日期：2026-09-21　轮次：第 22 轮

这套东西回答一个很窄的问题：**把「谁在选工具」换掉，用同一个任务集、同一套判据
再跑一遍，哪些任务退化、哪些持平、哪些变好。**

它不是新评测集，也不是新判定器：任务集来自 W4-01（288 条 / 8 类），时代与局面来自
W4-02 的生成器，判定器是那一个 `checkTask`。这里加进来的只有**可替换的 provider**。

## 1. 怎么用

```bash
node scripts/roco/shadow-replay.mjs --arm rule                      # 参考臂（不需要模型）
node scripts/roco/shadow-replay.mjs --arm local_4b                  # 真模型（要网关在线）
node scripts/roco/shadow-replay.mjs --arm local_4b --compare reports/roco/shadow-replay.json
```

产物：`reports/roco/shadow-replay.json`（参考臂）与
`reports/roco/shadow-replay-<arm>.json`（候选臂）。

## 2. 事实边界（写在代码里，也在这里）

- **模型只负责选工具。** 它给的参数照常走 `validToolArgs` 与真实引擎；
  不合法就是 `invalid-arguments`，与规则臂同一条路径、同一套记账。
- **状态版本由运行时覆盖**，不采信模型编的那个——状态版本是权威量，
  让模型改它等于让它自己给自己发过期豁免。
- **模型臂只问一次模型。** 多轮重试会让「选得准」与「试得多」混在一起。
- **拿不到模型就失败**，不静默回退到规则。回退会让「模型臂」悄悄变成规则臂，
  结论就成了「换模型没有影响」——一个看起来很好、其实什么都没测的结论。
  这条有测试钉住。
- 模型臂的失败原因进 `stopped`，逐条保留。

## 3. 本轮实测（2026-09-21）

**提示版本**：`prompt_digest = a5cb0fbcc53fbecd356b86f921030dac1954d737dfa1af731b452b2f04a6654d`
（产物里记着它；两份报告只有提示不同时，只比通过率是分不出差别的）。

| arm | 通过 | 通过率 | p50 延迟 |
|---|---|---|---|
| `rule`（参考臂） | **288/288** | 1.0000 | 0–1 ms |
| `local_4b`（本机 Qwen3.5-4B-4bit） | **225/288** | 0.7813 | 574–585 ms |

**重复性**：同一提示连跑两次给出**逐项相同**的结果（225/288、同样的类别分布、同样的
`stopped` 计数、同样的失败明细）。第一次跑得到 226/288，所以这台机器上的抖动是
**±1 条任务（0.35 个百分点）**，不是没有抖动——报数字时要带上这一条。

逐任务对比：**退化 62–63、扳回 0、都错 0**。退化**全部集中在两类**：

| 类别 | 参考臂 | 模型臂 | 退化 |
|---|---|---|---|
| `rules_lookup` | 72/72 | 32/72 | **40** |
| `roster_constraint` | 24/24 | 3/24 | **21** |
| `evidence_conflict` / `tool_failure` | 36/36 | 36/36、34/36 | 0–2 |
| 其余 4 类 | 全过 | 全过 | **0** |

`stopped` 分布：`complete` 171、**`invalid-arguments` 93**、`receipt-budget` 12、`policy` 12。

### 3.0 一次失败的提示实验（留痕，不藏）

试过把 `TOOL_CONTRACTS` 里的参数名逐条列进系统提示（`buildLocalToolSystem()`），
理由是「86 次失败里大多数是参数名不对，把契约写清楚应该能修」。
**实测是变差**：

| 提示 | 通过率 | `rules_lookup` | `roster_constraint` | `invalid-arguments` |
|---|---|---|---|---|
| v1（只列工具名 + kind 说明） | **0.7813** | 32/72 | 3/24 | 93 |
| v2（逐条列出参数名） | 0.7326 | 13/72 | 12/24 | 81 |

提示更长之后模型**更犹豫**：多出 27 次「什么都不查」和 12 次「去查当前位置」。
所以默认保留 v1；v2 的函数与产物都留着
（`reports/roco/shadow-replay-local_4b-promptv2.json`），随时可复跑。
**结论是负的，就照负的记。**

### 3.1 这张表说明什么（以及不说明什么）

**说明**：本机 4B 在**不需要精确参数**的六类上已经与规则臂持平
（工具失败、状态过期、证据冲突、静默、简短解释、继续停止）；
它的短板非常集中——**规则事实查询的 `kind`/定位参数**，以及**阵容类参数**
（要带 3 个稳定 id 与 `locked_pet`）。86 次 `invalid-arguments` 全是这类。

**这正是 W4-04 该训的东西**：不是「教它说话」，是教它把
`kind` + 定位参数 + 阵容三个 id 填对。这条结论现在有数字支撑，
而且**换任何 provider 都能用同一把尺子复测**。

补充一条从这次提示实验里学到的东西：**「把契约写进提示」不等于模型会用**。
v2 把参数名全列出来了，`invalid-arguments` 只从 93 降到 81，
而「什么都不查」增加了 27 次——瓶颈更像在**决定要不要查**，不在知不知道参数名。

**不说明**：这不是「模型不如规则」。规则臂在这一类上是**照着任务集写出来的**
（`hints` 里直接带着 `target_kind` 与 `target_args`），等于开卷；
模型臂拿到的是同一份提示，但它还要自己决定用不用。两臂**信息相同、机制不同**，
所以这张表量的是「当前提示 + 当前模型能不能把这些参数填对」，不是能力上限。

## 4. 错误轨迹目录（W4-02 的另一半）

```bash
npm run roco:model-errors      # → tests/evals/roco/model-error-trajectories-v1.jsonl
```

规则臂的 4,536 条在 `agent-trajectories-v1.jsonl`；这一份是**模型真的自己选工具**时
失败的 61 条，逐条给出**程序可判定的**失败分类与**候选**修复：

| 分类 | 条数 | 集中在哪里 | 候选修复的方向 |
|---|---|---|---|
| `asked-nothing` | **34** | rules_lookup 33 | 结构化输出约束（grammar/JSON），不是加长提示 |
| `wrong-args` | 13 | rules_lookup 6 / roster 7 | **参数级**监督（问题 → 正确的 kind + 定位参数） |
| `wrong-tool` | 13 | roster_constraint 13 | 按工具职责补路由说明 |
| `stopped-without-tool` | 1 | rules_lookup 1 | 收窄「默认停止」的边界 + few-shot 对照 |
| `budget-or-policy` | 0 | — | 不是模型缺陷，单列以免计入错误率 |

`candidate_fix` 是**候选**：没有任何一条被重新执行并确认修好，所以每条都带
`verified: false`，头部也写明这一点。把它读成「已经修好了」是错的。

### 4.1 这份目录抓出来的一个真问题（不在模型身上）

分类时发现 2 条 `tool_failure` 失败**账面上像模型文案问题，实际是模板不诚实**：
任务声明「这一手引擎答不了」，模型跑去查了规则集并拿到一份 `ok: true` 的摘要，
而 `finalAnswer()` 的模板在「有 ok 回执」这一支上就转通用回答，**没有**先说清
「这条答不了」。判挂是对的，但**原因会被记错**——记到模型头上，然后被当成训练目标，
去训一个根本不存在的能力。

修法在模板：只要局面声明了答不了这件事，正文必须先承认它，不管模型查到了什么。
修完重测，`tool_failure` 从 34/36 回到 **36/36**，整臂 **0.7813 → 0.7882**。

这也是这份目录的主要价值：**它把「谁该修」从账面印象里分离出来。**
没有它，这两条会被写进 SFT 的数据需求里。

## 5. 第一次 SFT：在**这台机器**上真的训出来了，但结论是「还不能上线」

第 33 轮用 mlx-lm 在本机（M5 Pro 48GB）跑了第一次 LoRA 微调——
**W4-04 的「硬件阻塞」在这台机器上其实并不成立**，之前把「目标机器是 M5 Pro 48GB」
读成了「本机做不了」，而本机就是 M5 Pro 48GB。

数据与配置（全部可复跑）：

| 项 | 值 |
|---|---|
| 数据 | `reports/roco/sft/{train,valid,test}.jsonl`，828 条（train 355 / val 197 / test 276） |
| 目标 | 来自**任务期望**（`expect.tool` + `args_must_match`），不是规则臂或模型的输出 |
| 切分 | 沿用任务集的 family 切分（**这一点后来被证明是关键**） |
| 配置 | mlx-lm 0.31.3，LoRA r=8、8 层、300 iters、lr 1e-5、mask-prompt、seed 20260921 |
| 训练 | 13 分钟，峰值内存 **16.1 GB**，可训练参数 0.096%（4.06M/4205.75M），train loss 0.029 |
| 适配器 | `.models/adapters/qwen35-4b-tool-v1/`（16 MB，gitignore） |

在**同一把尺子**上量（288 条任务门禁）：

| 指标 | 基座 | SFT v1 |
|---|---|---|
| 通过 | 225/288（0.7813） | **229/288（0.7951）** |
| `invalid-arguments` | 93 | **20** |
| p50 延迟 | 574–585 ms | **407 ms** |
| `rules_lookup` | 32/72 | 37/72 |
| **`roster_constraint`** | 3/24 | **0/24** |

**结论：不能上线。** 通过率涨了 1.4 个百分点、参数格式错误从 93 降到 20、
延迟降了三成——但 `roster_constraint` **整类归零**。

### 5.1 原因是切分设计，不是模型不行

那 24 条全部落在 **test 家族（A组三人-无锁定）**，而 SFT 的 train/val 里
**没有这个家族**——训练数据里每条都带着 `team` 与 `locked_pet`，
测试家族一条都没有。于是模型在那个家族上**只输出 `{"stop":true}`**（24/24 全是这样）。

这正是 family 隔离**该有的**表现：它把「换个阵容家族还灵不灵」变成了可观测的失败，
而不是让一个只在训练家族上有效的适配器蒙混过关。代价是：**按现在的切分，
这个适配器不可部署**——它缺一个家族的知识。

### 5.2 下一步（下一轮）

重建 SFT 数据时把**留出维度换成机制与表达模板**（任务集本来就是三重隔离的），
让每个家族在 train/val/test 里都出现；family 外泛化改用别的家族做评测。
然后**用同一套判据复跑**。基础管线（数据 → 训练 → 接适配器 → 同一把尺子）已经全部跑通，
所以那一步主要是重跑数据与训练，不是新建。

## 6. 明确不声称

- 不声称 4B 不能做这些任务：只说明**当前系统提示下**它在这 288 条上的表现；
- 不声称这是真人对话的分布：任务集是构造的、时代是引擎生成的；
- 不声称「退化 62」等于产品退化：任务集里 `roster_constraint` 的
  `locked_pet` 来自任务上下文，真实链路里它来自玩家操作，口径不完全相同；
- 不把通过率叫胜率（这里没有胜负，只有「判据过没过」）；
- 不声称 `candidate_fix` 有效：没有任何一条被重新执行验证过。
