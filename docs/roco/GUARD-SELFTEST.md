# 守卫自检：怎么证明「测试真的会红」

日期：2026-09-21　轮次：第 27 轮

## 1. 为什么需要它

这个仓库里最近四个真实缺陷**全部**是「测试全绿、实际是坏的」：

| 缺陷 | 谁抓到的 | 谁抓不到 |
|---|---|---|
| 浏览器模块图里出现静态 `node:*`，页面整条 import 链断掉 | 浏览器验收 | `test:unit`（Node 里 `node:fs` 存在） |
| 判定层的特征只读调用方传的字段，实际恒为 `null/0/0` | 手工量真实路径 | 单元测试（它按测试传的字段算） |
| 提示改了但产物没重跑，报告里的摘要与代码不符 | **没有**任何测试 | 全部 |
| 生成器改了但产物没重跑 | **没有**任何测试 | 全部 |

所以「有多少测试」不是有效指标，**「这些测试会不会红」才是**。

## 2. 做法：注入违规，看对应的测试挂不挂

对每条守卫，机械地做三件事：

1. 在**被测代码**里注入一个违规（一个真实的、会导致行为变坏的改动）；
2. 跑「应该抓到它」的那条测试；
3. 恢复文件。

判定：测试**必须失败**。仍然通过 → 这条守卫是**空的**。

第 27 轮的真实结果（4 条抽样，覆盖结构契约 / 报告装配 / 分类判据 / 判定层激活）：

| 注入的违规 | 对应守卫 | 结果 |
|---|---|---|
| 浏览器模块图里加一行静态 `import 'node:fs'` | 结构契约 | ✔ 红 |
| `prompt_digest` 改成恒 `null` | 阴影回放守卫 | ✔ 红 |
| 失败分类的 `match` 改成恒 `false` | 错误轨迹目录守卫 | ✔ 红 |
| 判定层的 `active` 恒 `false` | 判定层守卫 | ✔ 红 |

**其中两条一开始是绿的**，也就是两个真实盲点：

### 2.1 「生成器改了但产物没重跑」没有守卫

`test_agent_tasks.py` 的其它用例都在**内存里**重新 `build()`，而下游读的是**文件**。
把生成器里的期望参数改成工具不接受的键，所有用例照样绿，产物却仍是旧的。
补法：新增一条用例，在**独立子进程**里用 `--json` 重新生成，与仓库里的产物逐条比摘要。

（顺带发现 `build()` **不是幂等**的：它往模块级累加器里追加，重复调用只返回增量。
在进程内调用会把测试变成「靠调用顺序才能通过」——那种测试比没有更糟。
所以这条用例走子进程，并给生成器加了 `--json`，让一致性检查有一个稳定的输入。）

### 2.2 「报告装配逻辑被改坏」没有守卫

阴影回放的报告测试读的是**已落盘的**报告，于是改坏装配代码（例如把 `prompt_digest`
写成恒 `null`）不会有任何测试变色。补法：把装配抽成纯函数 `buildShadowReport()`，
测试**直接调它**，不经过文件。

## 3. 已经自动化：`npm run guard:selftest`

第 28 轮把手工做法变成了**登记表**（`scripts/roco/guard-selftest.mjs`）：
7 条注入，每条写明「抓的是什么」，跑完无论成败都恢复文件。登记项：

| 注入 | 抓的是什么 |
|---|---|
| 浏览器图里加静态 `node:fs` | 页面整条 import 链静默断掉（第 24 轮真发生） |
| 判定层 `active` 恒 false | 层接上了但永不生效（第 21 轮同类） |
| `prompt_digest` 恒 null | 两份报告分不出提示差异 |
| 失败分类 `match` 恒 false | 分类永不可达，把真问题藏起来 |
| 期望参数改成工具不接受的键 | 任务不可完成而测试全绿（W4-01 真发生） |
| 陪练 `sayable` 恒 true | 没素材也开口（P1 沉默率会掉） |
| 陪练去重恒失效 | 同一事实反复说（P5） |

复验结果：**7/7 全部变红**。

它同时被加进 `verify:release`（跑一次 8 秒），但**刻意不放进 `test:unit`**：
它逐个改写仓库文件再恢复，和并行跑的单测放在一起会互相读到注入中的状态——
第 28 轮实测把结构契约搞成偶发红。这类「会改文件」的检查必须串行。

### 3.1 自动化过程中又踩到一个真缺陷

从 `node --test` 里面再 `execFileSync('node', ['--test', ...])` 时，子进程继承了
`NODE_TEST_CONTEXT=child-v8`，于是它**不按参数跑那个测试文件**，永远 exit 0。
表现是自检把 **7 条注入全部报成「仍绿」**——看起来像所有守卫都失效，
实际是自检自己在测试运行器里跑不动。**真红被假绿盖住**，这是这个仓库里最危险的一类错误，
而它出现在「用来发现假绿」的工具自己身上。

修法：起子进程前清掉 `NODE_TEST_CONTEXT` / `NODE_TEST_WORKER_ID`（`childEnv()`），
并有测试钉住这一点。

## 4. 明确不声称

- 不声称所有守卫都通过了注入自检：只验了抽样出来的 4 条；
- 不声称注入集是穷尽的：只挑了 4 类最容易空掉的守卫；
- 注入自检**不替代**真实验收：它证明测试会红，不证明产品是对的。
